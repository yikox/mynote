> 目的：把 Codex 的分析、方案执行与简单任务分开，让主力模型保留判断力，同时把边界清晰的实施和长时等待交给合适的执行者。

## 核心分工

| 角色             | 模型与推理档位                  | 主要职责                                                                                 | 不负责                                           |
| ---------------- | ------------------------------- | ---------------------------------------------------------------------------------------- | ------------------------------------------------ |
| 主力模型         | GPT-5.6 Sol                     | 需求分析、方案设计、任务拆分、异常决策、最终验收与用户体验判断                           | 重复执行已经委托且闭环的工作                     |
| `luna_worker`    | `gpt-5.6-luna`，`max`           | 完整执行主力模型已经定稿、范围与边界清晰的计划；可以实施、修改、构建、测试并闭环交付     | 补做未决的关键方案决策、改变总体目标或扩大范围   |
| `spark_executor` | `gpt-5.3-codex-spark`，`medium` | 长时轮询、SSH 远程测试等待、进程/状态/日志检查，以及其他单一、简单、机械、边界明确的任务 | 方案设计、开放式调试、自行改变验收标准或扩大范围 |

## 路由判断

1. 需求、边界或实现路径仍需判断：由主力模型处理。
2. 方案已经定稿，需要完整实施和闭环验证：委托 `luna_worker`。
3. 工作是独立可切分的长时等待、轮询或简单机械步骤：委托 `spark_executor`。
4. Spark 遇到异常、超时或范围不清：停止并返回证据，不自行调试或改方案。
5. 主力模型根据异常重新决策；形成新方案后，再交 Luna 完整实施。

判断标准不是“任务耗时多久”，而是“是否需要复杂判断”。一个运行数小时但成功/失败判据明确的测试属于 Spark；一个只需几分钟但需要权衡架构和风险的任务仍属于主力模型。

## 长时轮询任务的委托信息

父 Agent 应只提供最小必要上下文，并明确：

- 远程目标和允许执行的命令；
- 测试或进程是否已经启动；
- 检查对象、轮询方式和超时时间；
- 成功标志、失败标志及需要保留的日志；
- 异常时停止条件和证据格式。

Spark 只负责按这些标准执行和报告。需要修改代码、重启服务、改变环境或开展开放式诊断时，必须交回主力模型。

## 手动验收

- 真实界面和关键交互优先用 Computer Use 验证。
- 固定、可重复、步骤明确的 Computer Use 验收交给 `spark_executor`。
- 主力模型保留最终用户体验判断和验收结论。
- 先用测试、脚本和构建完成机械验证，Computer Use 只覆盖关键路径，并优先使用局部截图。

## 委托原则

- 委托使用独立上下文，只传递完成任务所需的最小信息。
- Luna 对既定计划的整体执行结果负责；即使其中的简单子步骤交给 Spark，也不能丢失整体闭环责任。
- 父 Agent 不重复执行已经委托且完成的工作，只做验收、必要修正和最终汇总。
