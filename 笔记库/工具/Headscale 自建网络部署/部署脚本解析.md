# Headscale 部署脚本解析

> `headscale-setup.sh` 的逐段解析。VPS 侧一键部署：Headscale + Caddy + Embedded DERP + Exit Node。
>
> 本文按模块拆解，**所有代码块按顺序拼接即为完整脚本**。父笔记见 [Headscale 自建网络部署](../Headscale%20自建网络部署.md)。

## 为什么要脚本化

原方案是 23 步手工 SOP。手工执行有三个问题：

- 命令与版本绑定（`approve-routes` 在旧版叫 `routes enable`），抄旧教程必踩坑
- 中途失败后状态不明，不知道该从哪一步重来
- 部署完只能人肉核对验收清单，容易漏

脚本把这些固化下来，并在实际部署中修掉了 6 个 bug（见文末）。

## 四条设计原则

| 原则 | 做法 | 原因 |
| :--- | :--- | :--- |
| 幂等 | 每阶段先检测再执行 | 8Mbps/300ms 的链路上，下载和 API 调用失败概率不低，必须能直接重跑 |
| 失败即停 | `set -euo pipefail`，不自动回滚 | provisioning 场景里回滚到一半的状态最难排查 |
| 自验收 | 结尾跑 10 项检查 | 部署完自证成功，不依赖人肉核对 |
| 单一事实源 | 域名等全部参数化 | 迁移域名只需改参数重跑 |

## 脚本头与全局变量

```bash
#!/usr/bin/env bash
#
# Headscale 自建网络 —— VPS 侧一键部署
#
# 在 VPS 上执行，完成：Headscale + Caddy 反代 + Embedded DERP + Exit Node，
# 最后打印客户端接入命令。可重复执行（幂等），中途失败可直接重跑。
#
# 用法:
#   export DUCKDNS_TOKEN=xxxxxxxx
#   sudo -E ./headscale-setup.sh --domain zy-hs.duckdns.org --user zy
#
# 迁移到自有域名: 改 --domain 重跑即可，脚本会更新 server_url 并提示重新注册节点。

set -euo pipefail

readonly HEADSCALE_VERSION="0.29.3"
readonly HS_CONFIG="/etc/headscale/config.yaml"
readonly CADDYFILE="/etc/caddy/Caddyfile"
readonly NODE_HOSTNAME="vps-exit"

DOMAIN=""
BASE_DOMAIN=""
HS_USER=""
PUBLIC_IP=""
```

**版本必须锁死**。`HEADSCALE_VERSION` 写成具体值而非"最新版"，因为 headscale 的 CLI 命令是版本绑定的，浮动版本等于把最脆弱的地方交给未来。

`set -euo pipefail` 三件套：遇错即停、未定义变量报错、管道中任一环失败即失败。

## 输出与 JSON 解析辅助函数

```bash
# ---------- 输出 ----------

log()  { printf '\033[0;36m[%s]\033[0m %s\n' "$(date +%H:%M:%S)" "$*"; }
ok()   { printf '  \033[0;32m✓\033[0m %s\n' "$*"; }
warn() { printf '  \033[0;33m!\033[0m %s\n' "$*"; }
die()  { printf '\033[0;31m[失败]\033[0m %s\n' "$*" >&2; exit 1; }

step() { printf '\n\033[1;34m━━ %s\033[0m\n' "$*"; }

# JSON 一律用 python 解析。headscale / tailscale 的 JSON 是格式化输出，
# 键值之间带空格，用 grep '"key":"value"' 匹配不到。
json_query() { python3 -c "$1"; }
```

**这里藏着一个必踩的坑**：直觉上会写 `grep -q '"BackendState":"Running"'`，但 tailscale 输出的是格式化 JSON，实际长这样：

```json
"BackendState": "Running"
```

冒号后有空格，grep **永远匹配不到**，而且失败得很安静——脚本会以为服务没运行。所以 JSON 一律交给 Python 解析。

## 状态查询函数

```bash
# headscale 在列表为空时返回 JSON null 而非 []，直接迭代会抛 TypeError
user_id() {
    headscale users list -o json | json_query "
import sys, json
print(next(int(u['id']) for u in (json.load(sys.stdin) or []) if u['name'] == '${HS_USER}'))
"
}

# 节点名字段在不同版本里可能是 name 或 given_name，两个都认
node_id() {
    headscale nodes list -o json | json_query "
import sys, json
for n in (json.load(sys.stdin) or []):
    if '${NODE_HOSTNAME}' in (n.get('name'), n.get('given_name')):
        print(int(n['id'])); break
else:
    sys.exit(1)
"
}

# 当前 tailscaled 指向的控制面地址；未配置则为空
current_login_server() {
    tailscale debug prefs 2>/dev/null | json_query "
import sys, json
print(json.load(sys.stdin).get('ControlURL', '') or '')
" 2>/dev/null || true
}

exit_route_approved() {
    headscale nodes list -o json | json_query "
import sys, json
for n in (json.load(sys.stdin) or []):
    if '${NODE_HOSTNAME}' in (n.get('name'), n.get('given_name')):
        sys.exit(0 if '0.0.0.0/0' in (n.get('approved_routes') or []) else 1)
sys.exit(1)
"
}

tailscale_running() {
    tailscale status --json 2>/dev/null | json_query "
import sys, json
sys.exit(0 if json.load(sys.stdin).get('BackendState') == 'Running' else 1)
" 2>/dev/null
}
```

四个细节都是实际报错后加的：

- `json.load(...) or []`：headscale 在列表为空时返回 `null` 而非 `[]`，直接迭代抛 `TypeError`。首次部署必然触发
- `name` / `given_name` 双重匹配：`name` 是原始主机名（可能含中文，如 `zy的MacBook Air`），`given_name` 是规范化名（`zymacbook-air`）
- `current_login_server` 用 `tailscale debug prefs` 而非 `status --json`，后者不含 `ControlURL` 字段
- `exit_route_approved` 必须查 `approved_routes`。`nodes list-routes` 的文本输出里 Available 和 Approved 两列都含 `0.0.0.0/0`，grep 字符串会让未批准的情况也通过

## 参数解析

```bash
# ---------- 参数 ----------

parse_args() {
    while [[ $# -gt 0 ]]; do
        case "$1" in
            --domain)      DOMAIN="${2:-}"; shift 2 ;;
            --base-domain) BASE_DOMAIN="${2:-}"; shift 2 ;;
            --user)        HS_USER="${2:-}"; shift 2 ;;
            -h|--help)
                sed -n '2,14p' "$0" | sed 's/^#//'
                exit 0 ;;
            *) die "未知参数: $1" ;;
        esac
    done

    [[ -n "$DOMAIN"  ]] || die "缺少 --domain，例如 --domain hs.example.com"
    [[ -n "$HS_USER" ]] || die "缺少 --user，例如 --user zy"

    # 只有 DuckDNS 域名才需要 token 去更新解析；自有域名的 A 记录由用户自己配
    if [[ "$DOMAIN" == *.duckdns.org && -z "${DUCKDNS_TOKEN:-}" ]]; then
        die "DuckDNS 域名需要环境变量 DUCKDNS_TOKEN（用 sudo -E 保留环境变量）"
    fi

    # MagicDNS 的节点后缀。默认取 --domain 的父域加 ts 前缀：
    # hs.yiko.site → ts.yiko.site，节点即 gpu-01.ts.yiko.site
    [[ -n "$BASE_DOMAIN" ]] || BASE_DOMAIN="ts.${DOMAIN#*.}"
    [[ "$BASE_DOMAIN" != "$DOMAIN" ]] \
        || die "base_domain 不能与 server_url 域名相同，headscale 会拒绝启动"
}
```

**token 只从环境变量读，不做命令行参数**——命令行参数会进 shell history，密钥不该留在那里。

`BASE_DOMAIN` 自动推导：`hs.yiko.site` → `ts.yiko.site`。headscale 默认值是 `example.com`，会和真实域名撞名。

## 阶段 1：前置检查

```bash
# ---------- 1. 前置检查 ----------

preflight() {
    step "1/10 前置检查"

    [[ $EUID -eq 0 ]] || die "需要 root 权限，请用 sudo -E 执行"

    # 公网 IP：这台是 NAT 型 VPS，网卡上是内网地址，必须从出口探测
    for src in https://api.ipify.org https://ifconfig.me/ip https://icanhazip.com; do
        PUBLIC_IP=$(curl -sf --max-time 10 "$src" 2>/dev/null | tr -d '[:space:]') || continue
        [[ "$PUBLIC_IP" =~ ^[0-9]+\.[0-9]+\.[0-9]+\.[0-9]+$ ]] && break
        PUBLIC_IP=""
    done
    [[ -n "$PUBLIC_IP" ]] || die "无法获取公网 IP"
    ok "公网 IP: $PUBLIC_IP"

    local nic_ip
    nic_ip=$(ip -4 -o addr show scope global | awk '{print $4}' | cut -d/ -f1 | head -1)
    [[ "$nic_ip" != "$PUBLIC_IP" ]] && ok "NAT 型 VPS（网卡 $nic_ip），DERP 将使用公网 IP"

    # 80/443 不能被非 Caddy 的进程占用。重跑时 Caddy 已在监听，属正常
    local listeners
    listeners=$(ss -tlnpH "sport = :80 or sport = :443" 2>/dev/null || true)
    if [[ -n "$listeners" ]]; then
        local intruder
        intruder=$(printf '%s\n' "$listeners" | { grep -v 'users:(("caddy"' || true; } \
                   | awk '{print $4}' | tr '\n' ' ')
        [[ -z "$intruder" ]] || die "80/443 被非 Caddy 进程占用: $intruder"
        ok "80/443 由 Caddy 占用（重跑）"
    else
        ok "80/443 空闲"
    fi

    command -v curl >/dev/null || die "缺少 curl"
    python3 -c "import yaml" 2>/dev/null || die "缺少 PyYAML（apt install python3-yaml）"
    command -v dig >/dev/null || {
        log "安装 dnsutils..."
        apt-get install -y -qq dnsutils >/dev/null 2>&1 || die "dnsutils 安装失败"
    }
    ok "依赖齐备"
}
```

**公网 IP 必须从出口探测，不能用 `ip addr`**。腾讯云轻量是 NAT 型：网卡上是 `10.8.0.8`，公网 `43.155.173.41` 由虚拟化层映射。DERP 配置里若填了内网地址，客户端永远连不上，而且不会有任何报错——只是默默用不了。

端口检查这段有两个幂等设计：

- 允许 Caddy 占用 80/443（重跑时它已在运行），只拦截其他进程
- `{ grep -v ... || true; }` 的花括号不能省：`grep -v` 过滤光所有行时返回 1，`set -e` 下会**静默退出且无任何错误信息**

## 阶段 2：DNS

```bash
# ---------- 2. DNS ----------

setup_dns() {
    step "2/10 DNS 解析"

    if [[ "$DOMAIN" == *.duckdns.org ]]; then
        local sub="${DOMAIN%.duckdns.org}"
        local resp
        resp=$(curl -sf --max-time 20 \
            "https://www.duckdns.org/update?domains=${sub}&token=${DUCKDNS_TOKEN}&ip=${PUBLIC_IP}") \
            || die "DuckDNS 请求失败"
        [[ "$resp" == "OK" ]] || die "DuckDNS 更新被拒绝（返回 $resp），检查子域名与 token 是否匹配"
        ok "DuckDNS 已指向 $PUBLIC_IP"
    else
        ok "自有域名，A 记录由你自行配置"
    fi

    # 等待解析生效，证书签发依赖它。用 8.8.8.8 直查，绕开本机 resolver 缓存
    log "等待 DNS 生效..."
    local resolved
    for i in $(seq 1 30); do
        resolved=$(dig +short @8.8.8.8 "$DOMAIN" A 2>/dev/null | tail -1 \
                   || getent hosts "$DOMAIN" 2>/dev/null | awk '{print $1}' | head -1 || true)
        [[ "$resolved" == "$PUBLIC_IP" ]] && { ok "$DOMAIN → $PUBLIC_IP"; return; }
        sleep 5
    done
    die "DNS 未在 150 秒内生效（当前解析: ${resolved:-无}，期望 $PUBLIC_IP）
       自有域名请确认已添加 A 记录: ${DOMAIN} → ${PUBLIC_IP}
       Cloudflare 用户注意：必须关闭橙云代理（DNS only）"
}
```

**必须用 `dig @8.8.8.8` 直查，不能用 `getent`**。`getent` 走本机 resolver，刚配好 A 记录时大概率读到缓存里的 NXDOMAIN，白等 150 秒然后失败。

这一步是硬前置：Let's Encrypt 用 HTTP-01 挑战签证书，DNS 没生效则证书必然签不出来。宁可在这里明确失败，也不要拖到第 7 阶段变成一个模糊的"证书签发失败"。

## 阶段 3：防火墙

```bash
# ---------- 3. 防火墙 ----------

setup_firewall() {
    step "3/10 防火墙"

    apt-get install -y -qq ufw >/dev/null 2>&1

    # Exit Node 本质是转发，ufw 默认 FORWARD=DROP 会挡住
    if grep -q '^DEFAULT_FORWARD_POLICY="DROP"' /etc/default/ufw; then
        sed -i 's/^DEFAULT_FORWARD_POLICY="DROP"/DEFAULT_FORWARD_POLICY="ACCEPT"/' /etc/default/ufw
        ok "FORWARD 策略 DROP → ACCEPT（Exit Node 需要）"
    else
        ok "FORWARD 策略已是 ACCEPT"
    fi

    ufw --force default deny incoming >/dev/null
    ufw --force default allow outgoing >/dev/null

    # 22 必须先放行，否则 enable 的瞬间就失联
    ufw allow 22/tcp    >/dev/null
    ufw allow 80/tcp    >/dev/null
    ufw allow 443/tcp   >/dev/null
    ufw allow 3478/udp  >/dev/null
    ufw allow 41641/udp >/dev/null

    # tailnet 流量从 tailscale0 进来，不放行则 ssh vps-exit 不通
    ufw allow in on tailscale0 >/dev/null
    ok "规则: 22,80,443/tcp + 3478,41641/udp + tailscale0"

    ufw --force enable >/dev/null
    ok "ufw 已启用"
}
```

这一段有三个关键点，每个都对应一次实际故障：

- **端口规则必须一条一条写**。`ufw allow 22/tcp 80/tcp 443/tcp` 会报 `Wrong number of arguments`，ufw 不支持这种写法
- **`ufw allow in on tailscale0` 不能少**。tailnet 流量从 `tailscale0` 进来，被 `default deny incoming` 挡掉后现象很迷惑：公网 SSH 正常，`ssh vps-exit` 却不通，容易误判成 headscale 配错了
- **顺序不能反**。必须先 `allow 22/tcp` 再 `enable`，否则执行的瞬间就把自己锁在外面

`DEFAULT_FORWARD_POLICY` 那段单独说：Exit Node 本质是把流量从 `tailscale0` 转发到 `eth0`，走的是 iptables 的 FORWARD 链，而 ufw 默认策略是 DROP。

**注意**：ufw 之外还有云厂商的防火墙（虚拟化层），脚本管不到，必须在控制台单独放行。这是整个部署最容易卡住的地方。

## 阶段 4：安装 Headscale

```bash
# ---------- 4. 安装 Headscale ----------

install_headscale() {
    step "4/10 安装 Headscale v${HEADSCALE_VERSION}"

    if headscale version 2>/dev/null | grep -q "$HEADSCALE_VERSION"; then
        ok "已安装 v${HEADSCALE_VERSION}，跳过"
        return
    fi

    local deb="/tmp/headscale_${HEADSCALE_VERSION}.deb"
    local url="https://github.com/juanfont/headscale/releases/download/v${HEADSCALE_VERSION}/headscale_${HEADSCALE_VERSION}_linux_amd64.deb"

    log "下载中..."
    curl -fL --no-progress-meter --max-time 300 -o "$deb" "$url" || die "下载失败: $url"

    DEBIAN_FRONTEND=noninteractive apt-get install -y -qq "$deb" >/dev/null 2>&1 \
        || die "安装失败，查看: apt install $deb"
    rm -f "$deb"
    ok "$(headscale version 2>/dev/null | head -1)"
}
```

开头的版本检测就是幂等的体现：已装对版本直接跳过，重跑不会重复下载 20MB。

`.deb` 包会自动创建 `headscale` 系统用户、systemd service 和默认配置，省掉手工建用户和写 unit 文件。

## 阶段 5：配置 Headscale

```bash
# ---------- 5. 配置 Headscale ----------

configure_headscale() {
    step "5/10 配置 Headscale"

    [[ -f "${HS_CONFIG}.orig" ]] || cp "$HS_CONFIG" "${HS_CONFIG}.orig"

    # 变量名不能与脚本里的 readonly 同名，否则命令前缀赋值会报 readonly variable
    HS_CFG="$HS_CONFIG" HS_DOMAIN="$DOMAIN" HS_PUBIP="$PUBLIC_IP" \
    HS_BASEDOMAIN="$BASE_DOMAIN" python3 <<'PY'
import os, yaml

path = os.environ["HS_CFG"]
with open(path) as f:
    cfg = yaml.safe_load(f)

cfg["server_url"] = "https://%s" % os.environ["HS_DOMAIN"]
cfg["listen_addr"] = "127.0.0.1:8080"
cfg["metrics_listen_addr"] = "127.0.0.1:9090"
cfg["grpc_listen_addr"] = "127.0.0.1:50443"

# TLS 交给 Caddy
cfg["tls_cert_path"] = ""
cfg["tls_key_path"] = ""
cfg["tls_letsencrypt_hostname"] = ""

# 反代来自本机，否则 headscale 看到的客户端 IP 全是 127.0.0.1
cfg["trusted_proxies"] = ["127.0.0.1/32", "::1/128"]

derp = cfg.setdefault("derp", {}).setdefault("server", {})
derp["enabled"] = True
derp["ipv4"] = os.environ["HS_PUBIP"]
derp["verify_clients"] = True
# 本机无公网 IPv6。默认值是文档保留地址 2001:db8::1，留着会让客户端连不存在的地址
derp.pop("ipv6", None)

dns = cfg.setdefault("dns", {})
# MagicDNS 后缀。默认值 example.com 会和真实域名撞名
dns["base_domain"] = os.environ["HS_BASEDOMAIN"]
# 默认 true 会把客户端 DNS 强制换成 global nameservers(1.1.1.1)，
# 导致内网域名(NAS/路由器/打印机)全部解析失败。
# 改 false 后 MagicDNS 只管 tailnet 域名，其余交回本地 DNS。
dns["override_local_dns"] = False

with open(path, "w") as f:
    yaml.safe_dump(cfg, f, default_flow_style=False, sort_keys=False, allow_unicode=True)
PY

    chown headscale:headscale "$HS_CONFIG" 2>/dev/null || true
    ok "server_url = https://${DOMAIN}"
    ok "base_domain = ${BASE_DOMAIN}（MagicDNS 后缀）"
    ok "DERP ipv4 = ${PUBLIC_IP}（已移除无效的 ipv6）"
    ok "官方 DERP 保留（derp.urls 未改），自建与官方并存"

    headscale configtest 2>/dev/null || die "配置校验未通过，检查 $HS_CONFIG"
    ok "配置校验通过"

    # configtest 以 root 运行会创建 DERP 私钥，属主是 root，
    # 而服务以 headscale 用户运行，会因读不到密钥而启动失败
    chown -R headscale:headscale /var/lib/headscale
    ok "state 目录属主已归正"
}
```

这是整个脚本最关键的一段。几个要点：

**用 PyYAML 而非 sed 改配置**。sed 改 YAML 键值极其脆弱（缩进、注释、多层嵌套），PyYAML 解析成对象再改写是精确的。代价是丢失原文件注释，所以先备份成 `.orig`。

**三个必须覆盖的默认值**，每个都会造成真实故障：

| 配置项 | 默认值 | 不改的后果 |
| :--- | :--- | :--- |
| `dns.override_local_dns` | `true` | 客户端 DNS 被强制换成 1.1.1.1，内网域名全部解析失败 |
| `dns.base_domain` | `example.com` | 与真实域名撞名 |
| `derp.server.ipv6` | `2001:db8::1` | 文档保留地址，客户端会尝试连接并超时 |

**`chown -R` 那步是必须的**。`headscale configtest` 以 root 身份运行时会顺手生成 DERP 私钥，属主是 root；而服务以 `headscale` 用户跑，启动时读不到自己的密钥，报 `permission denied` 然后无限重启。这个因果链很不直观——校验配置的动作把服务搞挂了。

**环境变量名不能和脚本里的 `readonly` 变量同名**。写成 `HS_CONFIG="$HS_CONFIG" python3` 会直接报 `readonly variable` 退出，所以改名为 `HS_CFG`。

## 阶段 6：Caddy 反代

```bash
# ---------- 6. Caddy ----------

install_caddy() {
    step "6/10 安装 Caddy"

    if ! command -v caddy >/dev/null; then
        apt-get install -y -qq debian-keyring debian-archive-keyring apt-transport-https curl >/dev/null 2>&1
        curl -1sLf 'https://dl.cloudsmith.io/public/caddy/stable/gpg.key' \
            | gpg --dearmor -o /usr/share/keyrings/caddy-stable-archive-keyring.gpg
        curl -1sLf 'https://dl.cloudsmith.io/public/caddy/stable/debian.deb.txt' \
            | tee /etc/apt/sources.list.d/caddy-stable.list >/dev/null
        apt-get update -qq >/dev/null 2>&1
        apt-get install -y -qq caddy >/dev/null 2>&1 || die "Caddy 安装失败"
    fi
    ok "$(caddy version | head -1)"

    cat > "$CADDYFILE" <<EOF
${DOMAIN} {
    reverse_proxy 127.0.0.1:8080
}
EOF
    ok "反代 ${DOMAIN} → 127.0.0.1:8080"

    caddy validate --config "$CADDYFILE" --adapter caddyfile >/dev/null 2>&1 \
        || die "Caddyfile 校验失败"
    ok "Caddyfile 校验通过"
}
```

Caddyfile 只有三行，因为 Caddy 默认就做对了两件事：自动申请并续期 Let's Encrypt 证书、`reverse_proxy` 原生支持 WebSocket。

Headscale 的客户端连接依赖 WebSocket upgrade，用 Nginx 需要额外配 `Upgrade`/`Connection` 头，Caddy 不用。这也是 Cloudflare 橙云代理会破坏 headscale 的原因——它不支持 headscale 那种特殊的 POST upgrade。

链路：`Internet → Caddy:443 → Headscale 127.0.0.1:8080`，TLS 完全归 Caddy 管，所以 headscale 侧的 `tls_*` 全部置空。

## 阶段 7：启动服务与健康检查

```bash
# ---------- 7. 启动服务 ----------

start_services() {
    step "7/10 启动服务"

    systemctl enable --now headscale >/dev/null 2>&1
    systemctl restart headscale
    sleep 3
    systemctl is-active --quiet headscale \
        || die "headscale 未启动: journalctl -u headscale -n 50"
    ok "headscale 运行中"

    systemctl enable --now caddy >/dev/null 2>&1
    systemctl reload-or-restart caddy
    ok "caddy 运行中"

    # 本地健康检查
    curl -sf --max-time 10 http://127.0.0.1:8080/health >/dev/null \
        || die "本地健康检查失败"
    ok "本地 /health 正常"

    # 公网健康检查，同时验证证书签发。首次签发需要时间
    log "等待证书签发并验证公网可达（最多 90 秒）..."
    for i in $(seq 1 18); do
        if curl -sf --max-time 8 "https://${DOMAIN}/health" >/dev/null 2>&1; then
            ok "https://${DOMAIN}/health 正常"
            return
        fi
        sleep 5
    done
    die "公网 /health 不可达。常见原因：
       1) 云安全组未放行 80/443（ufw 之外的一层，需在控制台配置）
       2) 证书签发失败: journalctl -u caddy -n 50"
}
```

**分两级健康检查是有意的**：先测 `127.0.0.1:8080`，再测 `https://域名`。这样能区分故障域——本地通、公网不通，说明问题在 Caddy、证书或防火墙，而不是 headscale 本身。

失败信息里直接点出"云安全组"这个最可能的原因。实测中这一步卡住时，第一反应往往是去查 Caddy 日志和证书，而真正的原因在云控制台。

## 阶段 8：加入 tailnet

```bash
# ---------- 8. 加入 tailnet ----------

join_tailnet() {
    step "8/10 VPS 加入 tailnet"

    hostnamectl set-hostname "$NODE_HOSTNAME"

    command -v tailscale >/dev/null || {
        log "安装 tailscale..."
        curl -fsSL https://tailscale.com/install.sh | sh >/dev/null 2>&1 \
            || die "tailscale 安装失败"
    }
    ok "$(tailscale version | head -1)"

    headscale users list -o json | json_query "
import sys, json
users = json.load(sys.stdin) or []
sys.exit(0 if any(u['name'] == '${HS_USER}' for u in users) else 1)
" || headscale users create "$HS_USER" >/dev/null
    ok "用户 $HS_USER 就绪"

    # preauthkeys 要的是用户 ID（uint），不是用户名
    local uid
    uid=$(user_id) || die "无法解析用户 ID"

    # 转发必须在 advertise 之前开
    # 本机无公网 IPv6，但 tailnet 内部用 IPv6 ULA(fd7a::/48)，
    # 关掉 v6 转发 tailscale 会警告 exit node 可能异常。开启无副作用。
    cat > /etc/sysctl.d/99-tailscale.conf <<'EOF'
net.ipv4.ip_forward = 1
net.ipv6.conf.all.forwarding = 1
EOF
    sysctl -p /etc/sysctl.d/99-tailscale.conf >/dev/null
    [[ "$(sysctl -n net.ipv4.ip_forward)" == "1" ]] || die "IPv4 转发未生效"
    ok "IP 转发已开启（v4 + v6）"

    # 迁移域名时 tailscaled 仍连着旧控制面且状态是 Running，
    # 只判断 Running 会跳过重新注册，导致节点留在旧 server 上
    local want="https://${DOMAIN}" now
    now=$(current_login_server)

    if tailscale_running && [[ "$now" == "$want" ]]; then
        ok "已连接 $want，跳过注册"
    else
        [[ -n "$now" && "$now" != "$want" ]] && warn "控制面变更 $now → $want，重新注册"

        local key
        key=$(headscale preauthkeys create -u "$uid" --expiration 1h) || die "创建 preauthkey 失败"
        tailscale up \
            --login-server="https://${DOMAIN}" \
            --authkey="$key" \
            --hostname="$NODE_HOSTNAME" \
            --advertise-exit-node \
            --accept-dns=false \
            || die "tailscale up 失败"
        ok "已加入 tailnet 并 advertise exit node"
    fi
}
```

**用 preauthkey 而不是交互式登录**。原方案是 `tailscale up` 拿到 AUTH_ID 再去 `headscale auth register`，但 `tailscale up` 会阻塞等待认证，实操要开两个终端。preauthkey 一步到位。

**`preauthkeys create -u` 要的是用户 ID（uint），不是用户名**。而 `auth register --user` 反而接受用户名（string）——同一个工具里两个命令不一致，很容易踩。

**IP 转发必须在 `--advertise-exit-node` 之前开**，这是 tailscale 官方要求。IPv6 转发这台机器用不上（无公网 v6），但 tailnet 内部使用 `fd7a::/48` ULA 地址，关掉会让 tailscale 警告 exit node 可能异常，开着无副作用。

**控制面变更检测**是迁移域名的关键。只判断 `tailscale_running` 会有个隐蔽 bug：改域名重跑时，tailscaled 还连着旧控制面、状态就是 Running，于是跳过注册——节点留在旧 server 上，脚本却报成功。所以必须比对 `ControlURL`。

`--accept-dns=false` 让 VPS 自己不接受 tailnet 下发的 DNS，避免搞乱服务器自身的解析。

## 阶段 9：批准 Exit Node 路由

```bash
# ---------- 9. Exit Node 路由批准 ----------

setup_exit_node() {
    step "9/10 批准 Exit Node 路由"

    local nid
    nid=$(node_id) || die "找不到节点 ${NODE_HOSTNAME}"
    ok "节点 ID = $nid"

    headscale nodes approve-routes --identifier "$nid" --routes "0.0.0.0/0" >/dev/null \
        || die "路由批准失败"
    ok "已批准 0.0.0.0/0"
}
```

节点 advertise 了 exit node 之后，还需要控制面**批准**才真正生效——这是 headscale 的安全设计，防止任意节点自己声明成出口。

节点 ID 是动态的，必须查询获得，不能像原方案那样硬编码 `--identifier 1`。

批准 `0.0.0.0/0` 时 `::/0` 会联动批准，无需分别执行。

## 阶段 10：自验收

```bash
# ---------- 10. 验证 ----------

verify() {
    step "10/10 验收"

    local pass=0 fail=0
    check() {
        if eval "$2" >/dev/null 2>&1; then
            printf '  \033[0;32m PASS\033[0m %s\n' "$1"; pass=$((pass+1))
        else
            printf '  \033[0;31m FAIL\033[0m %s\n' "$1"; fail=$((fail+1))
        fi
    }

    check "https://${DOMAIN}/health 可达"      "curl -sf --max-time 10 https://${DOMAIN}/health"
    check "headscale 服务运行"                  "systemctl is-active --quiet headscale"
    check "caddy 服务运行"                      "systemctl is-active --quiet caddy"
    check "VPS 节点已注册"                      "headscale nodes list | grep -q ${NODE_HOSTNAME}"
    check "IP 转发已开启"                       "[[ \$(sysctl -n net.ipv4.ip_forward) == 1 ]]"
    # 必须查 approved_routes：list-routes 里 Available 和 Approved 都含 0.0.0.0/0，
    # 只 grep 字符串的话未批准也会误判为通过
    check "Exit Node 路由已批准"                "exit_route_approved"
    check "tailscale 在线"                      "tailscale_running"
    check "DERP 使用公网 IP"                    "grep -q '${PUBLIC_IP}' ${HS_CONFIG}"
    check "ufw 已启用"                          "ufw status | grep -q '^Status: active'"
    check "tailscale0 已放行"                   "ufw status | grep -q tailscale0"

    printf '\n  通过 %d / 失败 %d\n' "$pass" "$fail"
    [[ $fail -eq 0 ]] || die "有 $fail 项未通过"
}
```

十项检查覆盖了服务、网络、配置、防火墙四个维度，对应手工 SOP 里的验收清单。

**验证要查语义而非字符串**。`Exit Node 路由已批准` 这条最初写的是 `list-routes | grep -q '0.0.0.0/0'`，看起来对，实际上 Available 列也含这个字符串——未批准也会 PASS。这种"弱验证"比没有验证更危险，因为它给了虚假的安全感。

## 部署中实际修掉的 6 个 Bug

这些都是脚本首次运行时真实报错后修的，不是假想：

| # | 问题 | 现象 |
| :--- | :--- | :--- |
| 1 | `readonly` 变量作命令前缀赋值 | 阶段 5 直接崩溃 |
| 2 | `configtest` 生成 root 属主的 DERP 私钥 | 阶段 7 服务无限重启 |
| 3 | 重跑时把 Caddy 占用 80 端口误判为冲突 | 破坏幂等，无法重跑 |
| 4 | `grep -v` 过滤光所有行返回 1 | `set -e` 下静默退出，无任何错误信息 |
| 5 | `users list` 空列表返回 `null` 而非 `[]` | 输出 Python Traceback |
| 6 | 路由验证只 grep 字符串不查 `approved_routes` | 弱验证，未批准也会 PASS |

其中 3、4 两个特别值得记：它们不会让脚本报错，而是让脚本**以错误的方式"成功"或静默失败**，这类问题比崩溃更难查。
