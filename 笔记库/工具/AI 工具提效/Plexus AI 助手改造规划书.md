> 状态：方案已确认，待独立审核
> 规划范围：将 Plexus 当前被动式 AI 对话改造成可主动运行的 AI 助手
> 验收方式：自动化测试 + Computer Use 实际操作已安装的 Plexus 应用

## 1. 目标状态

### 1.1 最终产物

将现有 AI 页面改造成一个 AI 助手面板。系统只有一个长期存在的主助手，不在第一阶段拆分多个长期 Agent。

主助手可以：

- 按计划自动执行任务；
- 主动检查整个笔记库；
- 定时检索指定主题；
- 发现问题后主动发起对话；
- 记住用户偏好、任务、历史发现、处理决定和对话；
- 提出笔记修改建议，但未经确认不修改笔记。

### 1.2 核心使用场景

#### 主动检查笔记

助手发现重复笔记、相关但尚未建立联系的笔记、可能需要拆分的长笔记，以及内容疑似过时或冲突的笔记。

发现问题后，以 AI 对话消息主动告知用户，说明涉及笔记、判断依据和建议处理方式。

#### 定时检索主题

用户设置主题和执行时间，助手定时检索外部资料，与已有笔记比较，整理新增或变化的信息、来源及建议，并在助手面板中发起对话。

#### 用户主动交代任务

保留当前主动对话能力。用户可以临时要求助手检查笔记、整理知识、研究主题或执行其他任务；任务结果进入助手的运行记录和记忆体系。

#### 确认后执行修改

助手先发现问题并提出建议，用户确认后展示实际 diff，再执行写入、移动、拆分或删除操作。用户拒绝或取消时，笔记保持不变。

### 1.3 已确认的授权边界

- 助手可以读取整个笔记库；
- 助手可以读取完整历史和长期记忆；
- 助手可以执行已经配置的定时任务和主动巡检；
- 不增加每种能力单独开启的授权开关；
- 自动巡检和定时研究默认只读；
- 实际修改、移动、拆分和删除笔记仍必须经过用户确认。

### 1.4 明确不包含

- Plexus 关闭时运行；
- 多个独立的长期助手；
- 未经确认的笔记写入、删除、移动或发布；
- 独立的系统通知中心；
- 复杂的多 Agent 协作。

## 2. 验收与验证

### 2.1 验收原则

- 自动化测试验证数据、状态、调度、运行时和工具安全边界。
- 手动验收必须使用 Computer Use 操作已安装的 `/Applications/Plexus.app`。
- 手动验收不以 DOM 断言或单元测试代替，必须通过真实界面完成操作并记录结果。
- 手动验收应使用真实工作区中的测试笔记和可控任务数据，必要时保留截图或操作记录。
- 用户是最终验收人。

### 2.3 关键验收场景

#### 场景 A：发现重复笔记

```text

    ↓

    ↓
主动发起对话并说明依据
    ↓
用户要求给出合并方案
    ↓
助手生成合并建议和 diff
    ↓
用户确认后才修改
```

#### 场景 B：定时研究主题

```text
用户设置“每周检索 AI Agent”
    ↓
助手按计划执行
    ↓
对比上次结果和已有笔记
    ↓
发现新的重要信息
    ↓
在助手面板主动发起对话
    ↓
用户决定是否整理进笔记
```

#### 场景 C：助手记忆用户偏好

```text
用户确认“研究结果默认整理成独立笔记”
    ↓
助手记录该决定
    ↓
下一次研究任务自动采用相同方式
    ↓
用户无需重复说明
```

## 3. 当前现状与约束

### 3.1 已有能力

- Agent 已经是 Markdown 配置文件。
- `runAgent` 已经支持多轮流式对话、上下文压缩和工具调用。
- 工具已覆盖笔记读写、搜索、Web 搜索和 Git 检查。
- 写工具已有用户确认弹窗和 diff 回执。
- 会话持久化在 `.plexus/agent/sessions/`。
- AI 页面已有运行状态、模型选择、工具调用状态和上下文统计。
- `fs://changed` 已提供笔记文件变化事件。
- `.plexus/agent/` 已有插件私有数据目录和通用 watcher 事件。

### 3.2 当前缺口

- 没有定时任务模型和任务调度器。
- 没有助手主动发起消息的机制。
- 没有任务、运行、发现和长期记忆的独立存储。
- 没有笔记巡检和重复检测流程。
- 当前 AI 页面以普通会话和会话侧栏为中心，不是助手面板。
- `AgentRuntime` 以 `sessionId` 为核心，尚无后台任务运行适配层。
- 当前确认弹窗是单个全局请求，后台任务不能直接阻塞等待确认。

### 3.3 约束

- 只能在应用运行期间调度，暂不设计应用关闭后的执行。
- 自动任务必须默认使用只读工具。
- 后台任务不能弹出一个会长期阻塞的确认请求；应先生成发现或建议，用户回到助手面板确认。
- 任务必须绑定工作区，工作区切换时停止旧工作区任务并重新加载。
- 任务运行必须避免与用户手动对话并发争抢同一助手状态。
- 全库扫描不能每次无条件读取并发送全部笔记，应先做候选筛选，再交给 AI 判断。
- 记忆可以完整保存，但不能每次把全部记忆注入模型上下文，应使用相关性选择和压缩。

## 4. 候选方案与决策

### 4.1 方案 A：扩展现有 Session

将助手变成一个特殊 Session，所有定时任务都追加到该会话。

优点：改动少，复用现有会话、上下文和 UI。

缺点：自动任务、人工对话、发现、记忆和任务记录混在一起；后台任务容易污染对话上下文，并产生并发冲突。

### 4.2 方案 B：新增 Assistant 域，复用现有 Agent Loop

新增任务、运行记录、发现、记忆和调度器；模型调用、Context、Tools 和确认机制继续复用现有实现。

优点：助手状态和普通会话边界清晰；可以逐步增加主动能力；保留现有 AI 能力和安全门。

缺点：需要新增 Assistant Runtime、持久化结构、面板和调度器。

### 4.3 方案 C：Rust 后台统一调度

由 Rust 负责调度、存储和 AI 运行，前端只展示状态。

优点：未来更容易支持应用关闭后运行。

缺点：当前需求不需要；会重复实现前端已有 Agent 编排；增加跨端状态、事件和调试复杂度。

### 4.4 最终选择

选择方案 B：新增 Assistant 域，复用现有 Agent Loop、Context、Tools 和确认逻辑。

主助手使用当前选中的 Agent Definition 作为模型、提示词、上下文和工具策略来源；每次任务运行冻结一份配置快照，运行期间修改 Agent 文件只影响下一次任务。

主助手保留一条长期对话。自动任务不把完整工具过程直接塞进主对话，而是保存为独立运行记录，并将重要发现以精炼的助手消息投影到主对话中。

## 5. 目标数据模型

### 5.1 AssistantTask

表示可重复执行的任务，包含：

- id、名称、任务描述；
- 触发方式和执行时间；
- 是否启用；
- 上次运行时间和下次运行时间；
- 当前状态；
- 任务使用的 Agent 配置快照引用。

### 5.2 AssistantRun

表示一次实际运行，包含：

- id、taskId、工作区身份；
- 手动、定时或巡检触发来源；
- 开始和结束时间；
- 运行状态、耗时、错误和重试信息；
- 关联的发现和消息。

### 5.3 AssistantFinding

表示助手发现的问题，包含：

- 问题类型；
- 涉及的笔记路径；
- 判断依据和证据片段；
- 建议操作和可信程度；
- 新建、讨论中、已确认、已忽略、已完成等状态；
- 稳定指纹，用于避免同一个问题重复打扰。

### 5.4 AssistantMemory

记忆默认不限制类别，至少包括：

- 用户偏好；
- 已确认的写作和整理规则；
- 定时任务；
- 历史发现和处理决定；
- 任务运行结果；
- 主助手对话历史及其压缩摘要。

原始记录负责完整保存，Context 只按当前任务选择相关记忆，并沿用已有压缩机制生成模型可用的派生上下文。

## 6. 运行模型

### 6.1 任务触发

第一阶段支持：

- 用户在助手面板中手动运行；
- 按时间定时运行；
- 后续可接入笔记变化事件触发。

调度器只在应用运行期间工作。应用重新打开后，如果任务已经到期，默认只补跑一次，不连续补跑多个历史周期。

### 6.2 任务执行

```text
触发任务
    ↓
读取工作区和任务配置
    ↓
冻结 Agent / Model / Tool 快照
    ↓
本地候选筛选或准备搜索范围
    ↓
使用只读 ToolDispatcher 执行 Agent Loop
    ↓
保存 AssistantRun 和 AssistantFinding
    ↓
将重要结果投影为主助手消息
    ↓
等待用户对发现进行对话处理
```

后台运行入口使用只读 dispatcher，不允许直接执行笔记写入工具。用户确认后的修改由前台助手对话重新发起，继续使用现有确认弹窗和 diff。

### 6.3 面板结构

AI 助手面板建议包含：

- 主助手对话区；
- 待处理发现；
- 定时任务；
- 当前和历史运行记录；
- 记忆摘要或最近记忆；
- 历史普通 AI 会话入口。

## 7. 实施计划

### P1：助手面板骨架

- 新增 Assistant 状态和持久化结构；
- 建立固定的主助手会话；
- 将现有 AI 页面改造成助手面板；
- 保留普通历史会话；
- 增加任务、发现和运行记录的空态及展示结构。

交付标准：助手面板可打开，主对话不退化，状态可以保存和恢复。

### P2：Assistant Runtime 与任务调度

- 新增后台任务运行适配层；
- 复用现有 `runAgent`、Context 和 Tools；
- 新增任务创建、启停、运行和失败状态；
- 增加应用运行期间的定时调度；
- 增加任务串行队列和取消机制；
- 工作区切换时停止并重新加载任务。

交付标准：手动任务和定时任务都能执行，运行记录完整，后台任务不会等待写入确认。

### P3：笔记主动巡检

- 建立笔记候选筛选流程；
- 识别重复、相关、应拆分、疑似过时和冲突内容；
- 生成带证据的 AssistantFinding；
- 通过主助手对话主动告知；
- 对重复发现做稳定去重。

交付标准：测试笔记库中的明确正例能被发现，无关反例不会被标记为高可信问题。

### P4：定时研究

- 支持指定主题和执行周期；
- 调用 Web 搜索并保存来源；
- 对比上次运行结果和已有笔记；
- 只报告新增或变化信息；
- 在助手面板中主动发起对话。

交付标准：同一结果不会重复打扰，新增结果有来源且能关联已有笔记。

### P5：长期记忆

- 保存偏好、决定、任务、发现、运行和对话；
- 为记忆建立相关性选择；
- 复用现有上下文快照和压缩机制；
- 在助手面板中展示最近记忆和来源；
- 重启后恢复记忆并用于后续任务。

交付标准：助手能够在后续任务中使用此前确认的信息，且上下文不会因全部记忆注入而失控。

## 8. 风险与回退

| 风险 | 预防和应对 |
| --- | --- |
| 全库扫描成本过高 | 先做本地候选筛选，再交给 AI 判断；记录运行耗时和候选数量 |
| 自动任务与人工对话冲突 | 使用统一任务队列，同一主助手只允许一个主动运行；用户任务优先级更高 |
| 后台任务卡在确认弹窗 | 后台只读，发现问题后停止并等待前台确认 |
| 重复发现反复打扰 | 用工作区、问题类型、路径和证据生成稳定指纹 |
| 记忆无限增长 | 原始记录归档保存，模型上下文仅加载相关记忆并压缩旧叙事 |
| 工作区切换导致任务跑错 | 任务绑定工作区身份，切换时取消旧运行并重载新工作区任务 |
| AI 调用失败 | 持久化失败状态和原因，允许用户手动重试，不自动执行有副作用的重试 |
| 新面板影响旧会话 | 历史会话数据格式保持兼容，面板迁移失败时仍能打开普通会话 |

### 回退条件

- 助手后台任务出现未经确认的笔记修改；
- 任务状态与实际运行结果不一致；
- 主助手对话或历史会话无法恢复；
- 定时任务造成重复执行或持续打扰；
- 记忆加载导致主对话上下文不可用。

回退时优先关闭调度器和主动巡检，保留普通 AI 对话和现有工具调用能力；任务、运行和记忆数据不删除，等待修复后重新加载。

## 9. 独立审核要求

独立审核需要重点检查：

- AssistantTask、AssistantRun、AssistantFinding 和 AssistantMemory 的边界是否清晰；
- 固定主助手会话与普通 Session 是否兼容；
- 后台只读执行是否能够绕过所有写工具；
- 用户确认是否可能被后台任务阻塞；
- 任务调度是否会重复执行或跨工作区运行；
- 主动消息、任务记录和对话上下文是否会互相污染；
- 记忆的完整保存和上下文相关性选择是否一致；
- 方案是否存在可以进一步简化的部分。

审核结果按以下等级记录：

- 阻塞问题：不解决不能实施；
- 重要问题：可能导致较大风险或返工；
- 优化建议：不影响方案成立但可以提高质量；
- 待确认假设：规划依赖但尚未验证的条件。

审核完成后，问题应回流到对应的目标、验收、方案或实施计划阶段。
