## 1. 目标

Plexus 不预设笔记库应该采用什么结构，也不默认创建“拆分笔记、整理笔记、重复检查、定时研究”等内容自动化。

系统默认只提供一个长期主助手和通用基建。助手先建立两份经用户确认的基础认知：跨工作区共享的用户画像，以及每个工作区独立的笔记库章程。之后才依据这些规则观察笔记库变化、识别偏移并主动询问用户；普通记忆只补充具体偏好，不能替代基础认知。只有用户确认后的自动化才会进入调度器执行。

核心闭环：

```text
本地索引建立笔记库形状
    ↓
引导生成并确认用户画像与笔记库章程
    ↓
笔记发生变化
    ↓
助手脉冲进行中立观察
    ↓
发现值得理解的新现象
    ↓
带证据询问用户，不直接下结论
    ↓
用户决定更新规则、修正笔记库或记录例外
    ↓
形成可查看、可修改、可删除的记忆
    ↓
助手提出自动化草案并预览命中效果
    ↓
用户确认后才创建和调度
    ↓
每次运行产生可解释回执
```

### 1.1 产品原则

- 主助手是工作区内固定且唯一的产品身份，不展示或持久化 Agent 选择；文件化 Agent Definition 只属于普通 AI 会话，不能改变主助手身份或后台行为。
- 用户画像是真正的应用级全局数据，跨工作区共享；笔记库章程是工作区级数据，不跨库推断或串用。
- 当画像或章程缺失时，助手先读取本地索引与目录形状，再一次只问一个有依据的问题；不得用一张长表单让用户自行完成建模。
- 画像和章程都先生成可见草案，用户确认后才成为有效上下文；二者可查看、继续校准或重建。
- 默认自动化数量为零。“零自动化”准确指零条用户 `AssistantAutomation`；助手脉冲不创建 task/automation，不进入自动化计数或自动化调度队列。
- 助手默认不知道“好笔记库”应该是什么样子。
- 内置检测只能产生客观观察或候选，不能把长度、相似度、目录数量直接解释成问题。
- 主动发现以一个清晰问题结束，不以未经确认的整理建议结束。
- 同一问题没有新证据时不重复询问；用户忽略后，相关内容没有实质变化时不再出现。
- 所有记忆和自动化均可见、可追溯、可编辑、可停用、可删除。
- 后台运行保持只读；修改笔记继续使用现有确认与 diff 安全门。
- 不展示模型隐藏思维过程，只展示可验证的触发原因、输入范围、证据、工具、记忆和结果。
- Pulse 默认只运行本地索引和确定性观察；首次需要把正文交给模型做语义复核前，必须说明范围、provider 和费用边界并由用户允许。
- 主动询问遵守噪声预算：任一时刻最多一个未决问题，24 小时最多新增一个主动问题；不发系统通知、不抢焦点。
- 规则偏移不是错误判定。助手只展示章程条目、实际证据与差异，并询问用户选择“更新章程、修正笔记库、记为例外或忽略本次”。
- 用户可以主动提出时间触发或特殊条件触发任务；自然语言条件必须转成可见、可验证的结构化触发器，经预览和确认后才运行。

### 1.2 明确不包含

- Plexus 关闭时运行；
- 多个长期助手或多 Agent 协作；
- 预装内容整理模板并默认启用；
- 未经确认自动保存记忆或创建自动化；
- 未经确认修改、移动、拆分或删除笔记；
- 以原始运行日志或模型思维过程代替用户可理解的解释。

## 2. 核心概念

### 2.1 User Profile（全局用户画像）

用户画像保存跨笔记库稳定成立的目标和风格，包括：主要目标、写作风格、希望形成的笔记库类型、质量标准，以及希望助手扮演的角色。

- 真相位于应用级私有目录，不依赖某个工作区存在；
- 缺失时，助手先说明自己已知和未知的范围，一次只问一个问题；
- 助手认为信息足够后生成结构化草案，而不是直接写入；
- 只有用户确认的版本进入主对话、Pulse 和自动化上下文；
- 每次修改保留 revision、来源会话和确认时间，界面始终可查看与重新校准。

### 2.2 Library Charter（工作区笔记库章程）

笔记库章程描述当前工作区希望维持的形状，包括：用途、组织形式、命名规则、笔记粒度、生命周期、来源与图片约定、允许的例外。

助手在询问前先根据本地索引生成形状摘要，例如笔记数量、一级目录、目录分布、标题与层级模式；这些只作为提问依据，不能自动升级为规则。章程草案必须区分“用户明确要求”与“从现状观察到的证据”，确认后才成为有效规则。

用户画像回答“这个人通常想要什么”，笔记库章程回答“这个库具体应该怎样”。二者冲突时，以当前工作区已确认章程和用户本轮明确指令为准。

### 2.3 Assistant Pulse（助手脉冲）

助手脉冲是基础设施，不计入用户自动化。

- 工作区启动时执行一次轻量变化预检；
- 应用持续运行期间每两小时预检一次；
- 只有笔记相对上次索引发生变化时才进入观察阶段；
- 没有变化时只更新“上次观察、下次观察、跳过原因”，不向对话追加重复消息；
- 普通文件保存事件只标记索引/旧观察可能失效，不直接启动完整运行；
- 用户可手动点击“观察变化”，但重复点击必须合并；
- 脉冲可以暂停，但不伪装成用户创建的自动化。
- 新工作区或 v1 迁移后没有索引基线时，首次脉冲只静默建立基线，不生成观察、问题、模型调用、Run 或对话消息；只有用户手动点击“观察变化”才允许对全库建立首轮观察。

脉冲只负责发现“发生了什么”，例如路径变化、目录增长、标题或内容相似候选、长期累积、反复发生的用户操作。它不得仅凭固定阈值输出“应该拆分”或“应该合并”。

### 2.4 Observation（观察）

观察是可验证事实，至少包含：

- 来源脉冲或运行；
- 涉及路径与内容 hash；
- 发生时间和变化范围；
- 客观指标或内容片段；
- 观察生成方式：本地规则、AI 语义复核或 Web 来源；
- 指纹、状态和失效原因。

现有 `AssistantFinding` 的固定问题类型不再作为终态模型。旧发现迁移为只读历史或失效观察，不继续驱动默认提醒。

### 2.5 Inquiry（助手询问）

Observation 是事实，Inquiry 是面向用户的一个具体问题，两者不能混为同一状态。

询问至少保存：`observationId / question / evidenceFingerprint / status / deferredUntil / suppressionKey / answeredAt / staleReason`。

状态固定为：`pending / deferred / answered / suppressed / stale`。

- 同一 evidence fingerprint 只能存在一个有效询问；
- “稍后”到期后必须重新校验证据，不能直接恢复旧问题；
- “忽略这次”只关闭当前证据，内容实质变化后允许重新询问；
- “不再询问此类问题”保存 suppressionKey，不能因内容变化自动复活；
- 任一时刻最多存在一个待回答的主动问题；“稍后”期间不生成替代问题；
- 用户浏览历史消息时，新增询问不强制滚动到底部。

### 2.6 Alignment Review（规则偏移复核）

偏移复核比较“已确认的笔记库章程”与“当前本地索引形状”，只在以下时机执行：

- 章程确认后的首次基线；
- 默认每七天一次，且笔记库自上次复核后有变化；
- 出现一级目录增删、显著批量移动等结构性变化；
- 用户手动要求复核。

复核结果是结构化 `AssistantDriftReview`，包含关联章程 revision、证据路径、差异条目、状态与抑制信息。它只产生一个询问，不自动修改规则或笔记。用户可选择：更新章程、生成笔记库修正方案、记录为例外、忽略本次。章程 revision 变化后，旧复核全部失效。

### 2.7 Memory（补充记忆）

普通记忆只保存用户确认过、但不适合进入用户画像或笔记库章程的补充偏好和约束。基础认知固定分为三层：全局用户画像、工作区笔记库章程、工作区补充记忆；助手不能把三者混成一组不可解释的事实。

助手从对话中识别到候选记忆后，以气泡询问：

> 我准备记住：“推理优化目录采用章节结构，长笔记不因此拆分。”

用户可以选择“记住”“仅本次”“修改后记住”。未确认候选可以随投影持久化以支持重启恢复，但不能进入有效 `AssistantMemory` 集合，也不能被上下文选择器使用。

每条补充记忆显示内容、工作区作用域、稳定来源引用、创建时间、最近使用位置和关联自动化，并支持编辑、停用和删除。助手消息使用任何一层认知时必须分别列出画像 revision、章程 revision 和补充记忆引用。历史工作区私有的 `global` memory 仍按迁移规则降级为工作区记忆，不能冒充新的全局用户画像。

### 2.8 Automation（用户自动化）

自动化是用户确认后的通用配置，不再使用固定的 `inspection / research / user` 产品类型。

最小配置：

- 名称与目的；
- 指令；
- 触发条件；
- 作用范围与排除范围；
- 允许使用的工具；
- 什么情况下需要报告；
- 输出方式与固定的 `propose_only` 修改策略；
- 启用状态、上次/下次运行和版本号。

支持三类可解释触发器：手动、时间、工作区事件。时间触发包含固定间隔和受支持的日历计划；工作区事件首版支持 `note_changed` 与 `workspace_opened`，可配置路径范围、created/modified/removed 变化类型、最少变化数和静默聚合时间。事件先聚合再匹配，不能逐次保存直接调用模型。超出结构化能力的自然语言条件必须继续询问或明确标为暂不支持，不能藏进 instruction 假装已实现。

研究、Web 搜索、读取笔记、Git 检查是工具能力；“每周研究某主题”只是用户创建的一条自动化。

自动化生成流程：

```text
用户主动提出，或助手询问后用户明确要求
    ↓
通过现有 tool-call 通道生成 schema 校验后的结构化草案
    ↓
展示触发、范围、工具、报告条件和权限
    ↓
用户允许数据边界后执行一次显式只读 PreviewRun
    ↓
展示预计命中对象与示例输出
    ↓
用户确认后保存；否则不创建
```

主助手只能通过内部、非写入型的 `propose_automation` tool-call 产生 `AssistantAutomationDraft`，禁止从普通模型文本反向解析配置。草案至少包含 `instruction / trigger / scope / excludes / allowTools / reportPolicy / outputPolicy / revision`；该调用只创建投影草案，不能创建 Automation。

预览不进入正式调度队列。若预览需要模型、正文或 Web，执行前必须展示数据边界并由用户点击允许。最终确认操作原子地把 draft 转换为 Automation。第一阶段后台权限固定为 `mutationPolicy: propose_only`，不提供可能被理解为后台写入的权限开关；真正修改仍回到前台 diff 确认链。

### 2.9 Run Receipt（运行回执）

每次用户自动化和需要模型参与的助手脉冲都生成统一运行回执：

- 由什么触发；
- 为什么本次执行或跳过；
- 查看了哪些范围、多少笔记；
- 使用了哪些记忆；
- 使用了本地规则、哪个模型、哪些工具或哪些 Web 来源；
- 当前阶段、耗时、结果和失败影响；
- 是否产生问题、自动化草案或待用户决定事项。

回执默认折叠展示摘要，展开后显示可验证详情；不展示隐藏思维过程。

可信回执不能从 transcript 文本反向解析。实施透明 UI 前，先扩展现有运行边界，使 `runAgentCore` 返回或通过 `RunSink` 发出结构化 `RunOutcome`：`status / reason / requestIds / scope / model / memoryIds / toolReceipts / sources / usage / duration`。流失败、超时、取消和工具失败映射为不同终态；重试耗尽不得被记录为 succeeded。Assistant runner 只负责将 RunOutcome 保存并投影为 Run Receipt。

## 3. 交互设计

### 3.1 助手面板

```text
┌ Plexus 助手                              待命 ┐
│ 上次观察 09:00 · 下次 11:00 · 笔记无变化     │
│ [观察变化]  [自动化 2]  [记忆 4]             │
├───────────────────────────────────────────┤
│ 助手询问 · 本地观察 · 启动后发现              │
│ inbox 最近新增了 18 篇笔记，我还不知道它是     │
│ 临时收集箱还是长期分类。你希望如何使用它？      │
│                                             │
│ 依据：18 篇 / 最近 7 天 / 未调用 AI            │
│ [临时收集箱] [长期分类] [稍后] [不再询问]       │
├───────────────────────────────────────────┤
│ 普通对话与输入框                              │
└───────────────────────────────────────────┘
```

顶部状态必须回答：助手是否在工作、上次做了什么、下次何时运行、为什么跳过。计数都可以点击进入对应管理界面。

### 3.2 可解释消息

所有用户可见的主动事件继续使用对话气泡，但按语义区分：

- 助手观察；
- 助手询问；
- 记忆确认；
- 自动化草案；
- 自动化运行结果；
- 失败或失效。

气泡统一包含：类型、触发原因、时间、摘要、证据、数据边界和操作。点击“运行详情”查看范围、记忆、工具、模型、来源、耗时和跳过/失败原因。

旧观察涉及的笔记发生变化后，原气泡必须显示“已失效”，禁用旧操作，并提供重新观察入口。无变化的两小时脉冲只更新顶部状态，不制造对话噪声。

### 3.3 自动化管理抽屉

```text
自动化

每周跟踪本地模型部署进展              已启用
由 7 月 30 日对话创建
下次：周一 09:00 · 上次：发现 2 个新来源
[立即运行] [编辑] [暂停] [删除]

新建自动化入口：
[和助手一起创建]
```

编辑界面提供人类可读的手动、固定间隔、受支持日历计划和工作区事件条件，并实时展示下一次运行时间或事件匹配规则。删除自动化不删除历史运行回执。

### 3.4 助手认知抽屉

```text
助手认知

用户画像 · 全局 · revision 3
主要目标：沉淀可执行、可复用的技术知识
写作风格：结论优先、精炼、保留证据
[继续校准]

笔记库章程 · 当前工作区 · revision 2
组织：以知识节点和项目主题组织；inbox 只作临时入口
状态：7 月 30 日确认 · 下次复核 8 月 6 日
[复核规则] [继续校准]

“inbox 是临时收集箱，整理后应移出”
补充记忆 · 当前工作区 · 来源：8 月 3 日对话 · 被 1 个自动化使用
[编辑] [停用] [删除]
```

助手在回答或自动化运行中使用认知时，消息详情分别显示画像 revision、章程 revision 和补充记忆。

## 4. 数据与迁移

### 4.1 Schema v2

在现有 Assistant 域内升级 schema，不新增平行助手模块：

- `AssistantIndex` 增加不经过 task 队列的脉冲状态：`lastPulseAt / nextPulseAt / lastPulseOutcome / changedCount / paused / baselineReady`；
- 应用级 `AssistantUserProfile` 保存全局画像及 draft/confirmed 状态、来源、确认时间和 revision，真相位于 `~/.plexus/assistant/user-profile.json`；
- 工作区级 `AssistantLibraryCharter` 保存章程、索引形状证据、复核时间、例外、draft/confirmed 状态和 revision，真相位于现有 Assistant 私有数据区；
- `AssistantDriftReview` 保存章程 revision、差异、证据路径、用户决定和失效状态；
- `AssistantTask` 演进为通用 `AssistantAutomation`，移除固定业务类型，保留调度、状态和版本能力；
- `AssistantAutomationDraft` 保存经过 schema 校验但尚未确认的配置及 revision，只能由 `propose_automation` 产生；
- `AssistantRun` 增加阶段、执行/跳过原因、作用范围摘要、使用的记忆 ID、Automation revision/config snapshot 和结构化 `RunOutcome`；
- `AssistantFinding` 演进为中立 `AssistantObservation`；
- 增加 `AssistantInquiry`，保存问题生命周期、证据指纹、延后时间和永久 suppression key；
- `AssistantProjection` 增加引导、画像草案、章程草案、偏移询问等消息种类和关联 ID；
- `AssistantMemory` 继续只创建 workspace 补充记忆，并补充稳定 `sourceRef`、启用状态、`lastUsedAt`、关联自动化和 revision；
- Automation trigger 改为判别联合：manual、interval、schedule、workspace_event；事件触发保存路径、变化类型、最少变化数和聚合窗口；
- Assistant index 保存 `migrationState: pending | complete`，加载器必须容忍 v1、v2 和迁移中的混合状态。

持久化仍复用 `.plexus/agent/assistant/` 的原子写入与工作区隔离，不创建第二套事实源。

例外是全局用户画像：它不属于任一笔记库，使用同样的原子 JSON 读写策略保存在应用级私有目录；工作区关闭时仍可加载，但不能包含笔记正文或工作区路径。

### 4.2 迁移规则

- 首次迁移前保留不可变 v1 备份；迁移失败时展示 v1 只读数据，不能把版本不匹配当成空集合；
- 自动创建的旧 `inspection` 任务只从活动自动化集合移除，不迁移为用户自动化；历史 Run 保留配置快照或 `legacyTaskId`；
- 用户创建的研究任务迁移为只允许 `web_search` 的通用自动化，指令和原有受支持周期保持原意；
- 缺少明确指令或权限依据的旧 user task 迁移为 disabled legacy，不猜测配置；
- 旧发现和投影保留为历史消息，标记为 legacy/stale，不继续产生动作；
- 旧 projection 与 Session marker 使用稳定旧 ID 重建/去重，不能产生悬空的新引用；
- 现有已确认记忆保留在当前工作区；v1 global 标记不再解释为跨工作区共享；未确认或来源不明的记忆不得自动升级为有效偏好；
- 迁移幂等，失败时保留原文件并回退只读，不丢失历史会话；测试覆盖重复执行、单文件失败和迁移中途重启。

### 4.3 调度与并发不变量

- 调度队列只保存 `automationId / revision / workspace token`，不保存可能过期的完整配置对象；
- 出队前重新校验自动化仍存在、enabled 且 revision 一致；
- 暂停或删除立即移除未运行队项；运行中任务默认取消并等待结束；
- 每个 Run 冻结并保存完整 automation revision/config snapshot；
- Store 集合更新按域串行化或使用 CAS，避免 Pulse、runner 和 UI 同时整表写入造成丢失更新；
- PreviewRun 不进入正式调度队列，也不更新 Automation 的 lastRun/nextRun。

## 5. 实施计划

### P1：通用数据模型与迁移

- 升级 Assistant schema；
- 将固定任务演进为通用自动化；
- 增加脉冲状态、观察、询问、草案、消息种类和运行回执；
- 实现旧任务、发现、投影和记忆的幂等迁移；
- 删除启动时自动创建 `inspection` 用户任务的逻辑；
- 扩展现有运行边界产生结构化 `RunOutcome`，修正失败、超时、取消和重试耗尽的终态；
- 将 Store 更新收敛为不会丢失并发更新的串行/CAS 写入；
- 保留现有工作区代际、只读工具白名单、取消和投影幂等能力。

交付标准：新工作区默认零自动化；旧研究任务不丢失；旧内置巡检不再出现在自动化列表；迁移中断可恢复；运行失败不会被记录成成功。

### P2：助手脉冲与主动询问

- 将现有启动/两小时预检收敛为独立脉冲状态机；
- 没有基线时静默建立索引，不创建 Run、观察或消息；
- 没有变化时记录 skip receipt，只更新顶部状态；
- 有变化时先生成本地中立观察；未获授权不把正文交给模型；
- 在噪声预算内形成最多一个结构化 Inquiry；
- 问题必须引用观察证据，并标明是否调用模型、是否读取正文；
- 增加问题指纹、延后、单次忽略、永久抑制和内容变化后重新校验规则；
- 不再把关键词重合、长度阈值直接投影成固定整理建议。

交付标准：同一证据不会重复询问；未确认笔记库偏好时，助手不会直接宣称笔记应该拆分或合并。

### P3：透明消息与可信运行状态

- 为投影增加观察、询问、记忆确认、自动化草案、运行结果、失败/失效渲染；
- 增加统一的“运行详情”折叠区；
- 仅从结构化 RunOutcome 展示触发、范围、数据边界、记忆、模型、工具、来源、usage、耗时和原因；
- 顶部展示上次/下次脉冲及最近结果；
- 运行中气泡原位更新，不重复追加；
- 笔记变化后旧气泡显示失效并禁用动作。

交付标准：用户只看助手面板就能回答“为什么出现、看了什么、依据是什么、是否调用 AI、下一步要我做什么”。

### P4：用户发起的自动化引导、预览与管理

- 支持从用户请求，或助手询问后用户明确要求生成自动化草案；
- 通过内部 `propose_automation` tool-call 生成并校验 `AssistantAutomationDraft`，禁止解析普通文本；
- 草案展示目的、触发、范围、工具、报告条件、输出和权限；
- 用户允许数据边界后执行不入队的只读 PreviewRun，并显示预计命中对象；
- 用户明确确认后原子地持久化和启用；
- 增加自动化管理抽屉、状态、下一次运行、最近回执和立即运行/编辑/暂停/删除；
- 研究功能改为 Web 工具参与的通用自动化，不保留固定研究任务类型；
- 所有自动化后台运行继续禁止写入。

交付标准：用户可以通过对话创建一条符合自己笔记库习惯的自动化，确认前调度器中不存在该自动化。

### P5：透明记忆

- 对话中识别候选记忆，可随 projection payload 恢复，但不进入有效 Memory 集合；
- 通过气泡完成记住、仅本次、修改后记住；
- 增加记忆管理抽屉；
- 展示稳定来源、工作区作用域、启用状态、最近使用和关联自动化；
- 回答、询问和自动化运行回执展示实际使用的记忆；
- 编辑/停用/删除记忆后，下一次运行立即使用新状态。

交付标准：不存在用户无法查看的有效长期记忆；用户能追踪某条助手判断使用了哪些记忆。

### P6：清理与整体验收

- 删除被 v2 替代的固定发现类型、固定研究表单和废弃样式/测试；
- 更新 `architecture/modules/plugin-agent.md`、`architecture/main-design.md`（若模块入口或关系变化）和 `project.md`；
- 完成类型检查、前端全量测试、相关 Rust 测试和生产构建；
- 执行 `npm run install:local` 完整替换并启动 `/Applications/Plexus.app`；
- 使用 Computer Use 完成真实界面验收。

### P7：基础认知、偏移复核与条件触发

- 新增全局用户画像和工作区笔记库章程两个明确事实源；
- 主助手先读取本地索引形状，再以一次一个问题的方式引导，最终通过私有结构化工具生成可确认草案；
- 主对话和后台运行分别注入已确认画像、章程和补充记忆，并在回执中分开引用；
- 增加助手认知抽屉，展示状态、revision、来源、上次/下次复核，并允许继续校准；
- 章程确认后建立形状基线，按每周、有变化和结构事件的门禁进行确定性偏移复核；
- 偏移只投影证据与询问，支持更新章程、生成修正方案、记为例外或忽略；
- 自动化草案与调度器新增工作区事件触发，监听变化后按静默窗口聚合并匹配，禁止逐保存调用模型；
- 继续保持所有后台任务只读和 `propose_only`。

交付标准：新用户能从一个有依据的问题开始建立画像与章程；确认后助手可解释自己依据的规则；真实结构偏移只询问一次；用户可通过自然语言创建可见且可预览的时间或事件自动化。

### 已完成的首个闭环与本轮范围门

P1–P6 已交付静默基线、启动/两小时 Pulse、中立观察与结构化 Inquiry、确认补充记忆、用户主动提出的 Automation Draft、手动/固定间隔触发、只读 PreviewRun、确认后调度、结构化 RunOutcome 和可解释回执。

本轮只新增 P7 定义的全局用户画像、工作区章程、确定性偏移复核和 `workspace_event` 条件触发。不实现任意代码/任意自然语言表达式、关闭应用后运行、多助手协作或后台写入；无法可靠编译的特殊条件必须明确告知用户并继续澄清。

## 7. 关键验收场景

### 场景 A：助手不了解目录含义

```text
助手观察到 inbox 持续累积
    ↓
询问它是临时收集箱还是长期分类
    ↓
用户回答“临时收集箱”
    ↓
助手展示候选记忆，用户确认
    ↓
助手询问是否需要形成整理提醒自动化
    ↓
用户确认草案后才创建
```

### 场景 B：用户主动创建研究自动化

```text
用户说“每周关注本地模型部署进展”
    ↓
助手生成自动化草案
    ↓
展示每周时间、Web 搜索工具、输出规则和只读权限
    ↓
预览一次当前搜索结果
    ↓
用户确认后进入自动化中心
```

### 场景 C：运行回执解释一次跳过

```text
两小时脉冲到期
    ↓
索引确认笔记无变化
    ↓
不追加对话消息
    ↓
顶部状态更新为“10:46 已检查，笔记无变化，已跳过”
```

### 场景 D：旧观察失效

```text
助手基于 A、B 提出询问
    ↓
用户修改 A
    ↓
旧气泡标记“依据已变化”并禁用旧操作
    ↓
下次脉冲基于新内容决定是否重新询问
```

## 8. 实施约束

- 优先演进现有 Assistant store、scheduler、runner 和 projection，不新建平行运行体系；
- 保持模块对外接口最少，研究、观察和自动化共用已有 Tools 与运行内核；
- 迁移前后数据都必须可恢复，不用删除历史文件来简化实现；
- 测试使用可控时钟、固定 ID、固定 observation/model/search 夹具，不依赖真实两小时等待或真实网络；
- 确定性场景至少覆盖首次基线、无变化、同 fingerprint、证据实质变化、deferred/suppressed、迁移中断重启、队列中编辑/暂停/删除、模型失败和工作区切换；
- 每个实施阶段完成后运行相关测试；全部完成后运行全量测试并重新安装；
- 手动验收必须使用 Computer Use，不能只用 DOM 测试代替。

## 9. 实施结果（2026-08-04）

- 主助手已固定为工作区唯一产品身份，不再暴露或持久化 Agent 选择；默认用户自动化数量为零。
- 已落地跨工作区共享的用户画像、工作区独立的笔记库章程和工作区补充记忆；三层认知均可查看，画像与章程先形成草案，确认后才进入上下文。
- 已落地基于确定性笔记库形状的偏移复核；仅在章程已确认、达到复核时机且笔记发生变化时询问，同一证据不重复出现。
- 已支持用户主动创建手动、定时和 `note_changed` / `workspace_opened` 条件自动化；草案必须先通过只读预览，再由用户显式确认。
- 自动化执行时会重新校验工作区、revision、作用路径和排除路径；后台上下文冻结所选记忆与知识版本，运行回执可解释实际使用内容。
- 验证结果：前端 179 个测试文件、1206 项测试通过；Rust 150 项单元测试与 2 项边界测试通过；TypeScript、生产构建、DMG 本机安装均通过，并在 `/Applications/Plexus.app` 完成 Computer Use 验收。
