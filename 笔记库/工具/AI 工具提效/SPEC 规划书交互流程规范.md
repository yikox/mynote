# 规划书交互流程规范

> 版本：V1.0
> 适用范围：产品规划、技术方案、项目设计、功能开发、系统改造及其他需要形成正式规划书的任务。

---

## 1. 文档目的

本规范用于指导用户与 AI 共同完成一份可执行、可验证、可审核的规划书。

规划过程不应从“怎么做”直接开始，而应依次解决以下问题：

1. 最终目标是什么样的？
2. 如何证明目标已经实现？
3. 在现有条件下，应该选择什么方案？
4. 如何分阶段实施？
5. 规划中是否存在遗漏、冲突或不可执行的问题？

最终形成的规划书应满足以下要求：

* 目标明确；
* 范围清晰；
* 验收标准可执行；
* 方案能够覆盖目标；
* 实施计划具有可操作性；
* 风险和回退机制完整；
* 经独立审核后不存在阻塞问题。

---

## 2. 核心原则

### 2.1 先定义目标，再讨论方案

目标描述的是最终需要达到的状态，方案描述的是实现目标的方法。

在目标尚未明确之前，不应过早确定技术栈、系统架构或实现步骤。

### 2.2 目标必须能够验证

每个核心目标都应具备对应的验证方法和通过标准。

无法验证的目标应重新描述，或者明确标记为主观评价项。

### 2.3 方案必须建立在约束之上

规划不能只考虑理想状态，还需要考虑：

* 当前系统现状；
* 人力和时间；
* 技术能力；
* 预算和资源；
* 兼容性要求；
* 不可修改的边界。

### 2.4 方案与实施计划分离

方案回答：

> 准备采用什么方式实现目标？

实施计划回答：

> 按照什么顺序、由谁、在什么时候完成？

### 2.5 审核不是终点，而是回流机制

审核发现问题后，应根据问题类型返回对应阶段修改，而不是只在文档末尾增加补充说明。

---

## 3. 总体流程

```text
目标形态讨论
    ↓
验收与验证设计
    ↓
现状和约束确认
    ↓
候选方案比较与决策
    ↓
实施计划与里程碑
    ↓
AI 独立审核
    ↓
按问题类型回流修改
    ↓
形成正式规划书
```

对外可将流程概括为四个主阶段：

1. 目标定义；
2. 验收设计；
3. 方案与计划；
4. 独立审核。

其中，“现状与约束”“候选方案比较”和“审核回流”作为必要子流程包含在四个主阶段之中。

---

# 4. 阶段一：目标定义

## 4.1 阶段目的

通过用户与 AI 的讨论，明确最终希望实现的目标形态。

本阶段只关注“最终是什么样的”，暂不深入讨论具体实现方式。

## 4.2 核心问题

AI 应围绕以下内容与用户讨论：

### 最终产物

* 最终需要交付什么？
* 是产品、功能、系统、文档、工具，还是某种流程？
* 最终产物以什么形式存在？

### 使用方式

* 谁会使用？
* 在什么场景下使用？
* 核心使用流程是什么？
* 用户完成一次核心任务需要经过哪些步骤？

### 目标形态

* 最终界面、交互或运行状态是什么样的？
* 有无参考案例、竞品、截图、草图或已有实现？
* 哪些特征是必须保留的？

### 范围边界

* 本次规划包含哪些内容？
* 明确不包含哪些内容？
* 哪些内容可以延后处理？
* 哪些内容不能在本次项目中解决？

### 成功状态

* 项目完成后，用户希望看到什么变化？
* 与当前状态相比，需要改善哪些问题？
* 最重要的结果是什么？

## 4.3 注意事项

目标描述中应尽量避免直接加入实现方式。

例如：

不推荐：

> 使用 React 和微服务开发一个管理平台。

推荐：

> 建立一个面向内部团队的管理平台，使用户能够统一查看任务状态、处理异常并追踪执行记录。

只有在技术栈、平台或架构属于不可改变的硬约束时，才应在本阶段记录。

## 4.4 阶段产出

本阶段应输出《目标状态说明》，至少包括：

```markdown
## 目标概述

## 目标用户

## 典型使用场景

## 最终产物形态

## 核心使用流程

## 必须具备的能力

## 可选能力

## 明确不做的内容

## 参考案例

## 待确认问题
```

## 4.5 进入下一阶段的条件

满足以下条件后，才可进入验收设计：

* 最终产物已经明确；
* 核心使用场景已经明确；
* 必须具备的能力已经明确；
* 本次范围和非目标已经明确；
* 不存在影响整体方向的重大歧义。

# 5. 阶段二：验收与验证设计

## 5.1 阶段目的

将目标转化为可检查、可测试、可证明的验收标准。

本阶段需要回答：

> 如何证明规划中的目标已经实现？

## 5.2 验证设计内容

对于每个核心目标，AI 应提出：

* 需要验证什么；
* 采用什么验证方法；
* 需要什么环境、数据或工具；
* 什么条件下视为通过；
* 谁负责最终验收；
* 验证失败后如何定位问题；
* 哪些目标无法完全客观量化。

## 5.3 验收标准分类

### 功能验收

验证功能是否完整、正确。

示例：

* 用户能够创建、修改和删除任务；
* 操作完成后数据能够正确保存；
* 权限不足的用户无法执行受限操作。

### 性能验收

验证系统的速度、吞吐量和资源占用。

示例：

* 页面 P95 加载时间小于 1 秒；
* 单机支持每秒 100 个请求；
* 峰值显存占用不超过 16 GB。

### 稳定性验收

验证长时间运行和异常情况下的可靠性。

示例：

* 连续运行 24 小时无严重错误；
* 单个任务失败不会导致系统整体退出；
* 服务异常重启后未完成任务能够恢复。

### 易用性验收

验证用户是否能够顺利完成操作。

示例：

* 新用户无需培训即可完成核心操作；
* 核心任务操作步骤不超过 3 步；
* 关键错误能够给出明确提示。

### 兼容性验收

验证不同环境下的可用性。

示例：

* 支持指定版本的操作系统；
* 支持现有数据库和接口协议；
* 不影响旧版本客户端继续使用。

### 质量验收

验证结果是否达到预期质量。

示例：

* 图像结果 SSIM 不低于指定阈值；
* 数据准确率达到 99%；
* 输出结果经过人工抽样后无明显错误。

## 5.4 验收表模板

| 编号    | 目标   | 验证方式 | 验证环境或数据    | 通过标准       | 验收人   |
| ----- | ---- | ---- | ---------- | ---------- | ----- |
| V-001 | 示例目标 | 性能测试 | 测试环境与标准数据集 | P95 小于 1 秒 | 项目负责人 |
| V-002 | 示例目标 | 功能测试 | 标准测试用例     | 所有核心用例通过   | 测试负责人 |

## 5.5 无法客观验证的目标

对于“体验好”“结构清晰”“性能优秀”等模糊描述，应尽量转换为可验证标准。

例如：

原目标：

> 操作体验要好。

调整后：

> 核心操作不超过 3 步；失败时提供可理解的错误说明；首次使用者能够在 5 分钟内完成核心任务。

无法量化的内容可保留为人工评审项，但必须明确：

* 由谁评审；
* 按什么维度评审；
* 达到什么程度算通过。

## 5.6 阶段产出

本阶段应输出：

* 验收标准清单；
* 验证方案；
* 验证所需环境和数据；
* 暂时无法验证的项目；
* 验收负责人；
* 验收失败后的处理方式。

## 5.7 回流条件

出现以下情况时，应返回目标定义阶段：

* 核心目标无法设计验证方法；
* 不同人员对“完成”的理解明显不同；
* 通过标准依赖尚未明确的主观判断；
* 验收标准与原目标不一致；
* 一个目标包含多个相互冲突的结果。

# 6. 阶段三：方案与实施计划

本阶段包含三个子步骤：

1. 现状和约束确认；
2. 候选方案比较与决策；
3. 实施计划与里程碑。

---

## 6.1 现状和约束确认

### 6.1.1 阶段目的

在制定方案前，确认当前实际条件，防止产生脱离现实的规划。

### 6.1.2 需要确认的内容

#### 当前现状

* 当前已有系统是什么？
* 已经完成了哪些能力？
* 当前主要问题是什么？
* 是否存在历史方案或已有代码？
* 当前数据、接口和部署方式是什么？

#### 人力约束

* 有多少参与人员？
* 各自具备什么能力？
* 是否存在角色缺失？
* 谁负责决策、开发、测试和验收？

#### 时间约束

* 是否有明确截止时间？
* 哪些节点必须按时完成？
* 是否允许分阶段上线？
* 是否存在外部依赖时间？

#### 技术约束

* 必须使用或禁止使用哪些技术？
* 需要兼容哪些系统和版本？
* 是否有部署环境限制？
* 是否有性能、算力或存储限制？

#### 业务约束

* 哪些流程不能改变？
* 哪些数据不能迁移？
* 是否存在合规、安全或权限要求？
* 是否必须兼容历史用户习惯？

#### 资源约束

* 可用预算；
* 服务器和算力；
* 第三方服务；
* 数据和测试环境；
* 可使用的工具。

### 6.1.3 阶段产出

```markdown
## 当前现状

## 已有能力

## 当前问题

## 人力约束

## 时间约束

## 技术约束

## 业务约束

## 资源约束

## 不可修改项

## 可调整项

## 关键假设
```

## 6.2 候选方案比较与决策

### 6.2.1 阶段目的

根据目标、验收标准和约束，提出可行方案并进行选择。

原则上，不应在缺乏比较的情况下直接确定唯一方案。

### 6.2.2 候选方案类型

可以根据项目情况提供以下方案：

* 稳妥方案：改动较小，风险较低；
* 长期方案：结构更合理，长期维护成本更低；
* 快速验证方案：优先验证关键假设；
* 渐进式方案：分阶段替换或改造；
* 完整重构方案：适用于现有结构无法继续扩展的情况。

并非每个项目都需要多个方案，但至少需要说明：

* 为什么选择当前方案；
* 是否存在替代方案；
* 为什么不选择其他方向。

### 6.2.3 方案必须包含的内容

每个候选方案至少应说明：

* 核心思路；
* 主要模块；
* 关键流程；
* 如何满足目标；
* 如何通过验收；
* 对现有系统的影响；
* 实施成本；
* 主要风险；
* 回退方式；
* 适用条件。

### 6.2.4 方案对比表

| 维度      | 方案 A | 方案 B | 方案 C |
| ------- | ---- | ---- | ---- |
| 目标覆盖度   |      |      |      |
| 实施成本    |      |      |      |
| 开发周期    |      |      |      |
| 技术风险    |      |      |      |
| 对现有系统影响 |      |      |      |
| 可维护性    |      |      |      |
| 可扩展性    |      |      |      |
| 可回退性    |      |      |      |
| 验证难度    |      |      |      |

### 6.2.5 决策记录

最终选择方案时，应记录：

```markdown
## 最终选择

## 选择理由

## 适用条件

## 放弃的方案

## 放弃原因

## 关键假设

## 决策风险

## 需要后续验证的事项
```

## 6.3 实施计划与里程碑

### 6.3.1 阶段目的

将最终方案拆分为可以实际执行、独立验证和逐步交付的任务。

### 6.3.2 任务拆分原则

每个任务应尽量满足：

* 有明确的输入；
* 有明确的输出；
* 有负责人；
* 有完成标准；
* 有验证方式；
* 有依赖关系；
* 规模适中；
* 完成后能够判断是否成功。

避免使用以下模糊任务：

* 优化系统；
* 完善功能；
* 处理问题；
* 提升体验；
* 做好测试。

推荐改为：

* 完成任务状态查询接口；
* 将 P95 响应时间降低至 500 毫秒以内；
* 补充 20 个异常场景测试；
* 支持任务失败后自动重试两次。

### 6.3.3 里程碑设计

每个里程碑应形成可交付、可验证的阶段成果。

示例：

#### 里程碑 M1：关键假设验证

* 完成最小原型；
* 验证核心技术可行性；
* 输出性能基线；
* 确认是否继续采用当前方案。

#### 里程碑 M2：核心流程完成

* 完成主流程；
* 通过核心功能测试；
* 支持标准输入和输出；
* 暂不处理低优先级边界场景。

#### 里程碑 M3：完整能力交付

* 完成所有计划功能；
* 补齐异常流程；
* 完成性能优化；
* 通过完整验收。

#### 里程碑 M4：上线与观察

* 完成部署；
* 监控关键指标；
* 处理上线问题；
* 输出项目复盘。

### 6.3.4 实施计划表

| 编号    | 任务   | 负责人 | 前置依赖 | 输出物  | 验证方式        | 计划时间 | 状态  |
| ----- | ---- | --- | ---- | ---- | ----------- | ---- | --- |
| T-001 | 示例任务 | 待定  | 无    | 示例输出 | 对应验收项 V-001 | 待定   | 未开始 |

### 6.3.5 风险管理

每项主要风险应包含：

* 风险描述；
* 发生概率；
* 影响程度；
* 触发信号；
* 预防措施；
* 应对措施；
* 负责人。

| 风险   | 概率 | 影响 | 触发信号    | 预防措施     | 应对措施   |
| ---- | -- | -- | ------- | -------- | ------ |
| 示例风险 | 中  | 高  | 指标连续不达标 | 提前进行技术验证 | 切换备用方案 |

### 6.3.6 回退方案

对于重要改造，应明确：

* 哪些操作可回退；
* 回退到什么状态；
* 回退需要多长时间；
* 数据是否可恢复；
* 什么条件下启动回退；
* 谁拥有回退决策权。

# 7. 阶段四：AI 独立审核

## 7.1 阶段目的

由未直接参与方案制定的 AI，或以独立审核角色运行的 AI，对规划书进行系统检查。

审核 AI 不负责替原方案辩护，而应主动寻找：

* 遗漏；
* 冲突；
* 不可验证项；
* 不可执行项；
* 隐含假设；
* 过度设计；
* 风险缺口。

## 7.2 审核原则

审核应以规划书内容为依据，不得因为“看起来合理”就直接通过。

对于无法确认的内容，应明确标记为：

* 信息不足；
* 待验证假设；
* 需要用户决策；
* 需要补充证据。

## 7.3 审核维度

### 目标完整性

* 目标是否明确？
* 目标是否描述最终状态？
* 是否混入了未经确认的实现方式？
* 范围和非目标是否清晰？
* 是否存在相互冲突的目标？

### 验收完整性

* 每个核心目标是否有对应验收标准？
* 验收标准是否客观？
* 验收方法是否能够实际执行？
* 是否明确验证环境和数据？
* 是否存在无法判断完成状态的目标？

### 约束完整性

* 是否说明当前现状？
* 是否考虑人力、时间和资源限制？
* 是否考虑兼容性、安全和业务边界？
* 是否存在被忽略的不可修改项？

### 方案合理性

* 方案是否覆盖全部核心目标？
* 方案是否能够满足验收标准？
* 是否存在更简单的实现方式？
* 是否包含未经验证的关键假设？
* 是否存在明显过度设计？
* 是否考虑对现有系统的影响？

### 计划可执行性

* 任务是否可实际执行？
* 每个任务是否有明确输出？
* 依赖关系是否完整？
* 是否存在循环依赖？
* 里程碑是否能够独立验证？
* 时间安排是否与任务规模匹配？

### 风险完整性

* 是否识别主要风险？
* 是否有预防和应对方案？
* 是否定义回退条件？
* 是否考虑数据丢失、兼容失败和上线异常？
* 是否存在单点失败？

### 文档一致性

* 目标、验收、方案和计划是否一致？
* 同一概念是否存在不同表述？
* 编号和引用是否正确？
* 是否存在前后矛盾？
* 是否存在未关闭的待确认问题？

## 7.4 问题分级

审核结果应按以下等级分类。

### 阻塞问题

不解决就不能进入实施阶段。

例如：

* 核心目标不明确；
* 关键目标没有验收标准；
* 方案无法满足核心需求；
* 关键技术可行性未知；
* 实施计划存在严重依赖冲突；
* 缺少必要资源。

### 重要问题

不一定阻止实施，但可能导致明显风险或返工。

例如：

* 部分边界场景未覆盖；
* 风险应对不完整；
* 里程碑划分不合理；
* 方案对旧系统影响评估不足。

### 优化建议

不影响方案成立，但可以提高质量。

例如：

* 文档结构可以调整；
* 部分任务可以进一步拆分；
* 可以补充更多监控指标；
* 可以改善命名一致性。

### 待确认假设

规划依赖某个尚未证实的条件。

例如：

* 假设第三方接口稳定；
* 假设现有数据可以直接迁移；
* 假设性能瓶颈位于某个模块；
* 假设指定人员能够按时参与。

# 8. 审核回流机制

审核不是流程终点。发现问题后，应返回问题产生的阶段修改。

| 问题类型        | 返回阶段         |
| ----------- | ------------ |
| 目标不清晰       | 目标定义         |
| 范围冲突        | 目标定义         |
| 无法设计验收标准    | 目标定义或验收设计    |
| 验收方式不可执行    | 验收设计         |
| 现状或约束遗漏     | 现状与约束确认      |
| 方案无法覆盖目标    | 方案设计         |
| 方案依赖未经验证的假设 | 方案设计或增加验证里程碑 |
| 任务无法执行      | 实施计划         |
| 依赖关系错误      | 实施计划         |
| 风险和回退不完整    | 实施计划         |
| 仅存在文字和格式问题  | 直接修改文档       |

回流修改后，应重新执行审核。

当满足以下条件时，规划书可以定稿：

* 不存在阻塞问题；
* 重要问题已有处理结论；
* 所有关键假设都有验证计划；
* 目标、验收、方案和实施计划保持一致；
* 剩余风险处于可接受范围。

# 10. AI 交互规则

规划 AI 应遵循以下规则。

## 10.1 不过早生成完整方案

当目标仍然模糊时，AI 应优先帮助用户明确目标，不应直接输出完整技术方案。

## 10.2 一次集中解决一个阶段

推荐按照以下顺序交互：

1. 当前阶段提出问题；
2. 用户补充信息；
3. AI 总结本阶段结论；
4. 用户确认或修改；
5. 进入下一阶段。

## 10.3 区分已确认内容和 AI 假设

AI 输出中应明确区分：

* 用户明确提出的要求；
* 根据上下文推导的内容；
* AI 建议；
* 尚未验证的假设；
* 待用户确认的问题。

## 10.4 不重复询问已有信息

用户已经说明的内容应直接进入规划，不应在后续阶段反复询问。

## 10.5 信息不足时允许使用占位符

对于不影响总体规划的小项，可以使用：

```text
待确认
待负责人补充
实施前确认
根据测试结果决定
```

不得为了次要信息中断整个规划流程。

## 10.6 关键决策必须记录理由

对于会影响成本、周期、架构或后续维护的决定，应记录：

* 决策内容；
* 决策理由；
* 替代方案；
* 放弃原因；
* 适用前提。

# 11. 规划 AI 提示词模板

```text
你是一名项目规划助手。你的任务不是立即开始设计实现方案，而是与用户共同形成一份可执行、可验证、可审核的规划书。

请严格按照以下阶段工作：

第一阶段：目标定义
1. 明确最终产物是什么。
2. 明确目标用户和使用场景。
3. 描述目标最终形态和核心使用流程。
4. 区分必须能力、可选能力和明确不做的内容。
5. 在目标确认前，不要过早确定技术方案。

第二阶段：验收设计
1. 为每个核心目标设计验证方法。
2. 明确验证环境、数据、工具和负责人。
3. 给出客观的通过标准。
4. 对无法客观验证的目标，提出重新描述建议。
5. 如果目标不可验证，返回目标定义阶段。

第三阶段：方案与计划
1. 先确认当前现状、人力、时间、技术、业务和资源约束。
2. 根据目标、验收标准和约束提出候选方案。
3. 比较方案的成本、周期、风险、可维护性、扩展性和可回退性。
4. 记录最终选择及放弃其他方案的原因。
5. 将最终方案拆分为里程碑和可执行任务。
6. 每个任务都要有输出物、验证方式和依赖关系。
7. 补充风险、异常处理和回退方案。

第四阶段：规划书生成
1. 按统一结构生成完整规划书。
2. 明确区分已确认内容、AI 建议、关键假设和待确认事项。
3. 检查目标、验收、方案和计划是否一致。
4. 不得隐藏信息不足或未经验证的假设。

交互要求：
- 每个阶段结束时先总结阶段产出。
- 重大结论需要用户确认后再进入下一阶段。
- 不重复询问用户已经提供的信息。
- 对次要缺失信息可以使用占位符。
- 方案必须服务于目标和验收标准，不能为了技术复杂度而设计。
```

# 12. 审核 AI 提示词模板

```text
你是一名独立规划审核员。你没有参与该规划书的制定，也不需要为原方案辩护。

请从以下方面审核规划书：

1. 目标是否明确，是否描述最终状态。
2. 范围和非目标是否清晰。
3. 每个核心目标是否存在可执行的验收标准。
4. 验收方法、环境、数据和负责人是否明确。
5. 当前现状和约束是否完整。
6. 方案是否覆盖全部核心目标。
7. 方案是否能够通过既定验收。
8. 是否存在更简单、更低风险的替代方案。
9. 是否存在未经验证的关键假设。
10. 实施任务是否可执行，是否有明确输出物。
11. 任务依赖是否完整，是否存在循环依赖。
12. 里程碑是否能够独立交付和验证。
13. 风险、异常处理和回退方案是否完整。
14. 目标、验收、方案和计划是否前后一致。
15. 是否存在过度设计、范围蔓延或不必要复杂度。

请将问题分为：

- 阻塞问题：不解决不能实施；
- 重要问题：可能造成较大风险或返工；
- 优化建议：不影响实施但可以提高质量；
- 待确认假设：规划依赖但尚未验证的条件。

每个问题必须包含：

- 问题描述；
- 影响；
- 判断依据；
- 修改建议；
- 应返回修改的阶段。

最后给出以下结论之一：

- 通过；
- 有条件通过；
- 不通过。

不要只总结规划书内容，要主动寻找遗漏、冲突、不可验证项和不可执行项。
```

* [ ] 当前现状已经记录；

* [ ] 已完成独立审核；
* [ ] 不存在未解决的阻塞问题；
* [ ] 重要问题已有处理结论；
* [ ] 关键假设已有验证计划；
* [ ] 目标、验收、方案和计划保持一致。

# 14. 总结

本流程的核心逻辑是：

> 不可描述的目标不能规划。
> 不可验证的目标不能实施。
> 不考虑约束的方案无法执行。
> 不经过独立审核的规划不能定稿。

规划书的价值不在于提前写出所有细节，而在于建立一条清晰的路径：

```text
明确要达到什么状态
        ↓
明确如何证明已经达到
        ↓
根据现实条件选择方案
        ↓
拆分为可以执行的计划
        ↓
通过独立审核发现问题
        ↓
持续回流修改直至可实施
```
