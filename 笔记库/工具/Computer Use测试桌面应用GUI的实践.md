# Computer Use 在 Plexus GUI 测试中的使用体验

> 记录时间：2026-07-26  
> 范围：Plexus Markdown 活预览及表格内链接

## 总体感受

Computer Use 最有价值的地方，不是代替单元测试，而是从真实用户视角暴露“最终装配后才出现”的问题。

这次最典型的例子是链接键盘导航：组件测试已经证明链接是原生 `<a>`，但真正操作应用时，Tab 仍被 CodeMirror 的 `indentWithTab` 抢走。这个问题只看 DOM 或截图很难发现，通过真实按键和焦点观察才能确认。

整体体验：

- **视觉检查直观**：适合确认表格、frontmatter、注释、代码围栏等最终排版。
- **交互检查有价值**：鼠标、Tab、Enter 和焦点顺序能发现测试装配遗漏。
- **对环境较敏感**：旧应用、窗口焦点、权限重启、外部浏览器都会影响结果。
- **证据能力有限**：看到“像链接”不能证明协议安全或 DOM 语义，仍需代码和集成测试补充。

## 遇到的问题与处理结果

| 问题 | 实际体验 | 是否处理 |
| --- | --- | --- |
| 权限开启过程导致任务重启 | Computer Use 的授权过程打断了连续操作，需要重新连接上下文并确认当前应用状态 | **已处理**：恢复后从已有检查点继续，没有重做已完成步骤 |
| 容易操作到旧版应用 | `/Applications/Plexus.app` 与当前代码构建同时存在，仅看应用名无法判断版本 | **已处理**：使用独立的 `Plexus Dev.app` 和 bundle id `com.plexus.dev` |
| Tab 无法聚焦链接 | 链接虽然是原生 anchor，但 CodeMirror 的 `indentWithTab` 优先消费 Tab | **已处理**：增加生产级 Tab 路由，并在真实应用中复验三类链接焦点顺序 |
| 第一次 Tab 修复范围过宽 | 如果只判断“页面里有链接”，可能破坏标题、列表、表格、代码块等编辑场景的 Tab 行为 | **已处理**：收紧为单一空选区、顶层普通段落、可见且可聚焦链接；其他场景保持编辑器原行为 |
| 表格链接与普通单元格事件冲突 | 点击链接应导航，点击普通单元格应进入源码；两者都在同一个 widget 内 | **已处理**：链接消费交互事件，普通表面继续交给 CodeMirror |
| 外部链接打开后应用失去焦点 | Enter 会把操作带到外部浏览器，继续自动化会扩大测试范围 | **按边界处理**：只确认外部打开被触发，不继续控制浏览器；用文件 hash 证明笔记未被修改 |
| 视觉结果不能证明语义正确 | 截图能看到链接和高亮，却不能证明原生 `<a>`、危险协议拦截或文件未变化 | **已处理**：GUI 证据与 DOM 集成测试、协议测试、焦点检查和 SHA256 组合使用 |
| 临时笔记可能触发自动 Git 同步 | GUI 测试会真实写入笔记库，可能留下文件或同步记录 | **已处理**：使用唯一文件名，测试结束后通过应用删除并检查磁盘；不重写用户已有 Git 历史 |
| AI 消息验收可能调用付费模型 | 为验证固定 Markdown 的渲染而调用外部模型，成本高且结果随机 | **已处理**：直接向真实 `MessageItem` 输入固定 Markdown，验证 ReactMarkdown DOM |
| 截图证据存放在临时 worktree | 截图在当次复审中可用，但 worktree 清理后不再是长期证据 | **未完全处理**：下次需要把最终截图复制到持久化的验收目录 |

## Computer Use 实际发现了什么

### 1. 发现了生产装配中的 Tab 冲突

这是本次最有价值的发现。

自动化测试最初关注“链接是不是原生 anchor”“点击是否触发导航”，却没有装配完整的生产 keymap。Computer Use 真实按下 Tab 后，发现焦点没有进入链接，而是触发了编辑器缩进。

处理结果：

- 初步修复提交：`e75b3c9`
- 边界收紧提交：`b11f70c`
- 最终 GUI 中，焦点顺序为普通链接 → autolink → 裸 URL
- Enter 导航前后笔记 SHA256 一致

### 2. 验证了表格内链接的事件边界

Computer Use 能直接观察点击后的界面状态：

- 点击表格内链接，表格继续保持渲染状态。
- 点击普通单元格，表格恢复 Markdown 源码。

这比只断言 click handler 被调用更接近实际用户体验。

### 3. 暴露了“测试对象身份”问题

测试早期一度存在操作旧安装版应用的风险。Computer Use 会复用桌面上真实存在的窗口，因此应用身份必须显式隔离。

处理后，调试应用使用独立名称和 bundle id，避免旧版窗口、文件监听器和当前分支相互干扰。

## 没有完全交给 Computer Use 的部分

以下内容不适合只靠 GUI 判断：

- 危险 URL 协议是否被拒绝。
- 编辑器与 AI 的 Markdown AST 是否一致。
- 空白行内代码、数学公式、图片等高亮边界。
- 多光标、非空选区、不可见链接等大量组合。

这些部分由自动化测试和高级模型代码审查完成。Computer Use 负责最终人机交互，高精度语义仍由可重复的代码测试负责。

## 最终评价

本次遇到的产品阻塞问题都已处理，最终 12 项渲染问题全部关闭。

Computer Use 的优势是能发现：

- 真实键盘焦点问题。
- 鼠标事件所有权问题。
- 最终视觉和源码切换行为。
- 测试应用版本或窗口选错的问题。

它的主要限制是：

- 权限或会话重启会打断长流程。
- 桌面环境状态会影响可重复性。
- 视觉正确不等于语义正确。
- 外部浏览器、模型和自动 Git 等副作用需要主动限制。

结论：**Computer Use 很适合作为桌面应用的最终交互验收层，但必须与生产装配测试、文件状态校验和代码审查配合，不能单独作为“功能正确”的全部证据。**

## 可直接使用的提示词

下面这段适合用于桌面应用的 GUI 验收。使用前替换方括号中的内容：

```text
请使用 Computer Use 对 [应用名称 / 页面] 做一次真实 GUI 验收。

目标：
- 验证 [需要检查的视觉与交互行为]。
- 重点检查 [例如：表格内链接、Tab 焦点、Enter、右键、源码切换]。
- 发现问题时记录现象、复现条件、证据，以及是否已经处理。

开始前：
1. 先确认测试对象的应用路径、版本/commit、进程、窗口标题和 bundle id，避免操作到旧安装版。
2. 使用独立测试构建和唯一的临时数据，不修改我的现有内容。
3. 如果操作可能改变文件，先记录文件 hash 或其他可比较基线。
4. 权限申请或会话重启前先保存检查点；恢复后从检查点继续，不重复已经确认的项目。

测试时：
1. 分开检查视觉、鼠标交互、键盘焦点和数据是否被修改。
2. 键盘测试要观察真实焦点对象与顺序，不能只看页面外观。
3. 区分交互控件和普通表面：例如链接应导航，普通编辑区域应恢复源码或获得光标。
4. 截图只作为视觉证据；DOM 语义、协议安全、AST 和大量边界组合交给集成测试或代码检查。
5. 除非我明确授权，不继续控制外部浏览器、不调用付费模型、不发送外部消息，也不扩大测试范围。
6. 发现缺陷先稳定复现并记录。若任务包含修复，再修改代码、运行自动化测试，并用 Computer Use 复验原始症状。

结束时：
1. 删除临时数据并确认磁盘中不存在残留。
2. 对比操作前后的文件 hash，说明是否发生内容变化。
3. 不为清理测试痕迹而重写我的 Git 历史。
4. 按下表汇报，不要只说“测试通过”：

| 检查项 | 实际观察 | 证据 | 发现的问题 | 是否处理 | 剩余限制 |
| --- | --- | --- | --- | --- | --- |

最后单独总结：
- Computer Use 真正发现了哪些自动化测试没有发现的问题；
- 哪些问题已解决、部分解决或未解决；
- 哪些结论不是 Computer Use 单独能够证明的。
```
